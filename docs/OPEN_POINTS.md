32. License Verification Mechanism — Remaining Technical Details (mechanism scheme decided; central-server infra and tuning still open)

* Finalized logic (see Vision §5): The code is open to everyone, and no one can be physically prevented from running it on their own server — but the software does not function without connecting to ZonaryOS's central server and obtaining a valid license verification. License verification also determines which modules are active on that installation.
* Developer's raw idea (mechanism proposal, SUPERSEDED — see below): "Something like a complex hexadecimal process, GitHub Actions secrets and variables, combined with each file's MD5 and version-specific values, encrypting the files."
* **Decided this batch (`internal/license`, Never-Violate Rule 2's technical-friction layer): open question 4 is answered — YES, asymmetric signing with the secret kept server-side.** The Developer's original MD5-based raw idea is explicitly superseded, not implemented: MD5 is broken for any integrity/authenticity purpose, and a hash alone can't prove *authorized issuance* the way a signature can. Instead: a license token is a small JSON payload (firm/installation identifier, expiry, active module-key list) signed with Ed25519 (`crypto/ed25519`, no third-party crypto dependency) and base64url-encoded (`internal/license.Token`/`Sign`/`Verify` — see that package's doc comment for the exact wire format). This codebase holds only the Ed25519 **public** key (`ZONARYOS_LICENSE_PUBLIC_KEY`); it can verify a token but never mint one, since it never holds the matching private key. That private key exists only wherever an operator running `cmd/licensegen` (a stand-in test/dev issuing tool, explicitly NOT the real central-server issuance flow item 34 still needs to design) keeps it — never committed to this repository.
* **Also decided this batch: default-disabled is a structural, not incidental, property.** `internal/license.Verifier.Allow` — the single gate every call site uses — returns `nil` (allow) as its literal first statement whenever the verifier is nil or `ZONARYOS_LICENSE_ENFORCEMENT` is not exactly `"true"`. A deployment that never sets that env var runs every existing code path completely unaffected: no new checks, no new latency, no new failure modes, and it isn't even required to configure a public key or a token. Verified concretely in this batch (`internal/platformadmin/license_integration_test.go`'s `TestListFirms_LicenseEnforcementDisabled_BehavesExactlyAsBefore`, against a real Postgres instance) and by running the full E2E smoke test with enforcement left at its default off state.
* **Open question 2 (offline/grace-period behavior) has a mechanism now, but its exact tuning is still open**: `internal/license.Verifier` supports a configurable grace period past a token's expiry (`ZONARYOS_LICENSE_GRACE_PERIOD`) before failing closed, defaulting to a PROVISIONAL 72h (`internal/license.DefaultGracePeriod`) — matching `deploy/backup/backup-postgres.sh`'s own "PROVISIONAL DEFAULT, NOT A DECIDED SLA" precedent for an equally untuned number. Note this batch's honest limitation: there is no real central server yet (item 34), so today's "grace period" really means "how long past a locally-configured token's expiry to keep allowing access," not yet "how long to tolerate losing connectivity to a live license server" — the concrete network-offline scenario open question 2 originally asked about can only be fully answered once item 34's real server exists.
* **Open question 1 (verification trigger frequency) has a provisional answer, not a tuned one**: `internal/license.Verifier` re-checks the configured token every `RecheckInterval` (15 minutes, a background `time.Ticker` goroutine started from `cmd/server/main.go` only when enforcement is enabled) rather than only at process startup, so a long-running server process catches its own token's expiry crossing over time. 15 minutes is a judgment call, not a tuned number, and (as with open question 2) becomes a materially different question once a real network call to a central server exists.
* **Open question 3 (what exactly gets protected) has a narrow, honest answer for this batch, not a full one**: this batch protects license-token authenticity/expiry/module-activation data itself (via the Ed25519 signature) — it does **not** implement any executable-integrity/tamper-detection mechanism (the "protect the binary" half of the original raw idea). That remains open if it's ever wanted.
* **One real gate wired, deliberately narrow**: `internal/platformadmin.ListFirms` (`GET /api/platform-admin/firms`) now calls `license.Verifier.Allow(license.ModulePlatformAdmin)` after its existing allowlist check — chosen as the lowest-blast-radius illustrative fit (already allowlist-gated, already narrow read-only metadata scope, so a second orthogonal gate can't newly expose anything). This is a proof of mechanism, not a rollout: no other module (workflow engine create/transition paths, authentication itself, etc.) is gated yet. `internal/license`'s module-key list (`workflow_engine`, `audit_trail`, `platform_admin`) is itself a small, honest, provisional stand-in for item 30's still-fully-open real module/pricing catalog — do not read it as that catalog.
* **Still genuinely open** (not resolved by this batch): item 34's real central license-issuing server (this batch's `cmd/licensegen` is explicitly a local/test stand-in, not that infrastructure); item 30's real module/pricing catalog (concrete module list, band thresholds, unit prices); the exact, tuned values for verification-trigger frequency and grace-period duration (both are currently defensible-guess provisional defaults, not Developer-approved SLA numbers); any executable-integrity/tamper-detection mechanism (open question 3's "protect the binary" half, not attempted here).

34. Deployment Target / Infrastructure (interim decision made; final production target still open)

* Found while building out the CI pipeline's checklist items (see CLAUDE.md's "How to Verify a Change"): a "Canary/Rollback Trigger" CI check is listed as part of the eventual acceptance bar, but there is no decided deployment target or infrastructure for ZonaryOS to actually deploy to yet (checked: not in Vision, not elsewhere in this file) — Vision §4 only fixes the *database* topology (single global primary + read-only replicas, active-passive, automatic failover), not where/how the application binary itself gets deployed, released, or rolled back.
* Investigation findings (research/recommendation only — no infrastructure, Dockerfiles, or CI changes committed):
  1. **Current state: nothing in the repo containerizes the app itself yet.** The only container artifact in the repo is `docker-compose.yml`, and it covers just the two *dev dependencies* (Postgres, Keycloak) — there is no `Dockerfile` anywhere for the Go backend (`cmd/server`) or the Next.js frontend (`web/`). Whichever deployment target gets picked, writing those app Dockerfiles is unavoidable first work, independent of the provider choice.
  2. **Option A — managed container PaaS (e.g. Fly.io, Railway, Render):** lowest setup complexity — these platforms build straight from a Dockerfile with no separate IaC/registry/networking setup, and would get ZonaryOS to a real deployed environment fastest. Cost shape is usage-based and cheap at small scale, but less favorable than reserved cloud pricing at larger scale. Multi-region fit varies a lot by vendor: Fly.io has native multi-region deploy support (anycast + regional volumes) that can approximate Vision §4's active-passive layout; Railway/Render are comparatively single-region-oriented today, so picking one of those would mean deferring true multi-region until a migration later. Canary/rollback: these platforms expose a native staged-rollout primitive (e.g. `fly deploy --strategy=canary`, Render's blue/green environments) — the CI "Canary/Rollback Trigger" check under this option is concretely "call the platform's deploy CLI with its canary flag, then call its rollback API if post-deploy health checks fail," the least CI work of any option here.
  3. **Option B — major cloud provider managed container/VM service (AWS ECS/Fargate, GCP Cloud Run, Azure Container Apps):** most literal match to the already-fixed Vision §4 topology — all three have real cross-region managed-Postgres replica + failover mechanisms (e.g. RDS/Aurora cross-region replicas + Route 53 failover, Cloud SQL cross-region replicas) that can implement "single global primary + N read replicas + automatic failover" directly, rather than approximating it. Setup complexity is meaningfully higher: real IaC (Terraform/Pulumi or console-driven), a container registry, VPC/IAM setup, on top of the same not-yet-written app Dockerfiles — this is multi-week infrastructure work for a small team, not a weekend task. Cost shape is more granular/controllable at scale (and has small free tiers for early testing) but requires more deliberate cost management than a PaaS's flat usage billing. Canary/rollback: each provider has a native traffic-splitting primitive (Cloud Run traffic percentages, Container Apps revision splitting, CodeDeploy blue/green target groups) that a CI job could drive, but designing and testing that pipeline is a project of its own, not a single CI job addition.
  4. **Option C — self-hosted/bare-metal:** not recommended to pursue now — there's no concrete driver for it yet. The two plausible reasons to prefer it (cost at scale, and data residency if item 33's KVKK question requires certain data to stay within a specific jurisdiction) are both still unresolved/hypothetical: there's no live traffic to have real cost-at-scale numbers, and item 33 hasn't determined whether jurisdictional data residency is actually required. If item 33 later concludes a jurisdiction-locked requirement, the realistic shape would be one targeted regional node participating in the broader active-passive layout (e.g. a Turkey-based replica/primary), not a wholesale in-house infrastructure replacement — reinventing DB failover/orchestration from scratch is an ongoing ops burden the team's current size doesn't support. Not padded further since no concrete trigger exists today.
* Claude's recommendation (not adopted as policy without Developer sign-off, per this file's own Rule 1): given the team's current size and that no app containerization exists yet at all, **Option A (a managed container PaaS, specifically one with real multi-region support like Fly.io) is the pragmatic starting point** — it gets a real deployed environment and a working canary/rollback CI check soonest, with the least new infrastructure to build and maintain. Option B (a major cloud provider) would be the natural next step if/when multi-region becomes an immediate rather than eventual need, or if the PaaS's multi-region story proves insufficient in practice. Option C isn't worth adopting until item 33's KVKK question actually forces it.
* Remaining questions needing the Developer's actual decision:
  1. Which track to commit to — Option A (managed PaaS), Option B (major cloud provider), a deliberate "defer further, revisit later" — or Option C if there's a data-residency/cost driver not captured above?
  2. If Option A or B: which specific vendor/provider? (No preference is stated anywhere in Vision/Rules; this investigation surveys categories, not a specific vendor pick.)
  3. Budget bracket — deliberately not proposed here; that's the Developer's call, not Claude's, per this task's own instruction.
  4. Should this decision wait on item 33 (KVKK/data-residency) resolving first, in case that forces a bare-metal/regional-node component into whatever gets picked?
* **Interim decision (Developer): Oracle Cloud Always Free (Ampere A1, arm64) as a near-term dev/test deployment target - explicitly not a production commitment.** This does not resolve the four open questions above (final production target, vendor, budget, item-33 timing all remain open) - it only unblocks getting a real, containerized, non-local environment running now. See `docs/DEVELOPMENT.md`'s "Running the full stack in containers" section for what was built: portable `Dockerfile`/`web/Dockerfile` (multi-arch, no cloud-specific base images or assumptions) and a `docker-compose.yml` full-stack (Postgres, Keycloak, backend, frontend), verified end-to-end locally (a full interactive login round-trip plus wizard -> firm -> stock -> sell) before any Oracle step. Oracle-specific steps (security-list/firewall rules) are kept separate from the portable Docker layer on purpose, so a later move to a paid PaaS/major cloud provider isn't blocked by anything decided here. Caveats that keep this from being mistaken for production: no SLA, no automatic backup, single region/single instance (not Vision §4's active-passive/multi-region topology), and Oracle can reclaim Always Free capacity under pressure. Follow-up: the instance is now provisioned and reachable, and a real reverse-proxy deployment package (`docker-compose.prod.yml`, `deploy/nginx/zonaryos.conf`, `docs/DEPLOYMENT.md`) exists to make the stack reachable at `https://zonaryos.duckdns.org` (shared with other unrelated sites on the same box) rather than only `localhost` - designed and verified locally, handed off to the Developer to run since this doesn't resolve any of the four open questions above either.

39. Permission-Tag CI Check's Dynamic-Key Blind Spot (new — surfaced while building the automated Rule 7 check)

* Background: this batch built `web/scripts/check-permission-tags.mjs` (CI job `permission-tag-check`), the static, AST-based counterpart to Permission Audit Mode's runtime overlay - closing the gap flagged by a prior architecture audit that Rule 7 ("every permission-gated UI element must carry a permission tag") was only enforced by a developer remembering to open Audit Mode and look. The check verifies that every qualifying interactive element (`<button>`, an element with `onClick`, a `<form>` with `onSubmit`, an `<a>`/`Link` with `href`) carries a literal `data-permission-key` or `data-permission-public` JSX attribute - purely syntactic (attribute-name presence), not full type-flow analysis, same scoping choice `check-i18n-strings.mjs` already made for its own `{t(...)}` calls.
* Remaining open question: for an element whose `data-permission-key` value is a *dynamic* expression rather than a literal string - e.g. `Workflow/WorkflowInstanceList.tsx`'s `data-permission-key={action.permissionKey}`, one tag key per available workflow action, necessarily dynamic since the set of actions is data-driven - the check only confirms the attribute is *present*, not that the expression it's bound to actually resolves to a real, non-empty permission-catalog key at runtime for every code path. A future refactor that accidentally passes `undefined`/an empty string through that prop chain would still pass this check today. Closing that gap for real would need either (a) full type-flow analysis tracing the expression back to its source (a materially bigger, slower check, explicitly out of scope for what this batch built - see the script's own header "Limitation" note), or (b) a narrower, targeted runtime assertion (e.g. Permission Audit Mode's own overlay already effectively catches an empty string as "no `permissionKey` set" → renders as untagged, so there may already be a live-mode backstop for this specific case - not confirmed against every current call site as part of this batch).
* Not resolved here: this batch's task was explicitly scoped to building the static coverage check itself, not extending it into type-flow analysis or auditing every current dynamic-key call site for correctness - flagged here as the one real remaining gap rather than treated as silently complete.
