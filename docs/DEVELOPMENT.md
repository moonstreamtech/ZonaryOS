# Development Setup

This document covers local setup for the ZonaryOS application (backend + frontend). For product scope and architecture decisions, see `docs/VISION.md`. For working rules, see `CLAUDE.md`.

## Prerequisites

- Go 1.24+
- Node.js 22+
- Docker (for Postgres and Keycloak)

## Backend

```
cp .env.example .env   # adjust as needed
make build
make test
make run                # starts the server on :8080
```

`GET /healthz` returns `{"status":"ok"}` once the server is up.

## Frontend

```
cd web
cp .env.example .env.local
npm install
npm run dev              # starts the frontend on :3000
```

The frontend serves locale-prefixed routes (`/en`, `/tr`) via `next-intl`; `/` redirects to the default locale. All UI copy comes from `web/messages/{locale}.json` — no hardcoded strings (see `CLAUDE.md`, Never-Violate Rule 4).

## Local infrastructure (Postgres, Keycloak)

```
make dev-up      # starts Postgres (:5433 - see "Running the full stack in containers" below for why not :5432) and Keycloak (:8081) via docker-compose
make dev-down     # stops them
```

### Fallback: no Docker registry access

Some sandboxed CI/agent environments allow general internet/GitHub access but block Docker registries (Docker Hub, `quay.io`) outright - `make dev-up` will fail there with an image pull error, even though nothing is actually wrong with the compose file or the realm config. In that specific situation only, use:

```
make dev-up-standalone      # starts Postgres natively + Keycloak as a standalone JVM process
make dev-down-standalone    # stops the Keycloak process (Postgres is left running, as a shared system service)
```

`scripts/dev-up-standalone.sh` starts Postgres via the local `postgresql` service (a real, natively-running Postgres, on its OS default port `5432` - **not** `5433`, which is specific to `make dev-up`'s containerized Postgres, see "Running the full stack in containers" below for why they differ) and downloads Keycloak's standalone distribution from **GitHub Releases** (`github.com/keycloak/keycloak`, not a Docker registry - a genuinely different network path) into `.zonaryos/keycloak-standalone/` (gitignored), then runs it with `bin/kc.sh start-dev --import-realm`, importing the exact same `deploy/keycloak/zonaryos-realm.json` the Docker path uses. Both paths produce the same realm/client/user, verified identically by `internal/identity`'s tests - which path started Keycloak doesn't matter to the application. **If you're running the "Running the X tests" sections' `ZONARYOS_TEST_*_DATABASE_URL` exports below against `make dev-up-standalone` instead of `make dev-up`, use `5432` in place of the `5433` shown there.**

Prefer `make dev-up` whenever Docker registries are reachable; this is a narrow fallback for one specific failure mode, not a general Docker replacement.

#### Claude Code Remote sessions on this project: use `make dev-up-standalone`, not `make dev-up`

Verified 2026-07-31, after three prior Remote sessions had each independently reported "no Docker daemon available" and skipped Postgres integration tests / the E2E smoke test as a result. The actual situation is narrower than "no Docker":

- The Docker CLI, `dockerd`, `containerd`, and `runc` are all installed (`docker-ce`, `docker-ce-cli`, `docker-buildx-plugin`, `docker-compose-plugin` via apt) - but the daemon is not started by default (no `/var/run/docker.sock`, no running `dockerd` process). Running `dockerd` manually (as root, which this environment runs as) starts it successfully - `docker version` then shows a working client and server.
- With the daemon running, `docker pull` of any public image still fails - not a daemon problem, a network policy one. The registry manifest/auth handshake succeeds, but the actual image layer download is rejected: `docker pull postgres:16` fails on `Get "https://production.cloudfront.docker.com/registry-v2/.../data?...": Forbidden`. Querying this environment's egress proxy directly (`curl http://127.0.0.1:$HTTPS_PROXY_PORT/__agentproxy/status`, see `/root/.ccr/README.md`) confirms it: `recentRelayFailures` shows a `connect_rejected` / `403` for `production.cloudfront.docker.com:443` - Docker Hub's CDN blob-serving host is not on this session's egress allowlist, even though the Docker Hub registry/auth hosts themselves are reachable. This is an organization network policy, not a bug to route around or retry.
- `make dev-up-standalone` sidesteps this entirely, and was confirmed to fully work in this environment: `postgresql-16` is already apt-installed (no image pull needed), and Keycloak's standalone distribution downloads straight from `github.com/keycloak/keycloak`'s GitHub Releases - a different host than any Docker registry, and one this environment's egress policy does allow.

**Conclusion for future Remote sessions on this project: don't spend time re-diagnosing "Docker isn't available" - it's a known, understood, and already-worked-around network policy gap. Go straight to `make dev-up-standalone`.** It is not a degraded substitute for verification purposes: run against it today, the full suite - `go test -p 1 ./...` with all `ZONARYOS_TEST_*` env vars set (including `ZONARYOS_TEST_KEYCLOAK_*`, i.e. the real Keycloak integration test, not just the Postgres ones) - passed, and `scripts/e2e_smoke_test.sh` passed end-to-end against the real standalone-started Postgres, Keycloak, backend, and built-and-started frontend.

This does mean the one CI Checklist item still without an *automated* run anywhere (`internal/identity/keycloak_integration_test.go` - see the Continuous Integration section below on why the `integration-tests` CI job itself excludes it) is now something a Remote session can actually execute, not just a human on a laptop. Recommendation: treat "run `make dev-up-standalone` and the full `go test -p 1 ./...` suite, including the Keycloak integration test" as a standing, expected step for any PR touching `internal/identity` or the full stack - not because it's newly possible (it already was, on a laptop), but because a Remote session no longer has an excuse to skip it and report "untested" instead.

`make dev-up` automatically imports `deploy/keycloak/zonaryos-realm.json` into Keycloak on startup (via `start-dev --import-realm`, mounted read-only into the container's `data/import` directory). This is the "realm as code" mechanism for this repo - a plain realm export JSON, not Terraform: it needs no extra tool or apply step, and Keycloak applies it automatically the moment the container starts, matching the zero-extra-steps `make dev-up` workflow the rest of local dev already uses.

The imported realm (`zonaryos`) contains:
- **Client `zonaryos-web`**: public client, Authorization Code + PKCE (S256), redirect URI `http://localhost:3000/*` - used by the frontend's login flow (see below). Direct Access Grants (the OAuth2 password grant) is also enabled on this client, but **only as a local dev/test convenience** so integration tests and quick `curl` checks can obtain a token without a browser - this is not a production security posture and this realm is never used outside local dev (production Keycloak/realm configuration is managed separately, outside this repo).
- **Dev user** `dev@zonaryos.local` / `zonaryos-dev` - for manually exercising the login flow at `http://localhost:3000/api/auth/login`.

**Keycloak's role in this system is identity only.** It authenticates a user and issues a token asserting who they are (`sub`, `email`, `name`); it holds no ZonaryOS authorization data. Which firms a user belongs to and what role they hold in each lives entirely in ZonaryOS's own tables (`users`, `firms`, `roles`, `user_firm_roles` - see below) - a firm's dynamically-created custom roles (Vision §3's parametric permission system) are never synced into Keycloak.

### Backend: verifying tokens and resolving identity

`internal/identity`:
- `Verifier` (`verifier.go`) discovers the realm's OIDC configuration and verifies a bearer token's signature, issuer, expiry, and `azp` (authorized party) claim against the configured client ID.
- `Middleware` (`middleware.go`) enforces this on any route it wraps, attaching the resulting `Identity` to the request context.
- `ResolveOrCreateUser` (`user.go`) upserts the verified identity into the global `users` table by `keycloak_subject`.
- `Memberships` (`membership.go`) lists every firm a user belongs to, and `RoleInFirm` resolves their role within one chosen firm by opening a normal `db.WithFirmContext` transaction - proving the full chain from a verified token to an RLS-scoped database session.

Two HTTP endpoints exercise this end to end: `GET /api/me` (identity + firm memberships) and `GET /api/me/firms/{firmID}/role` (role within one firm - 403s if the caller isn't actually a member, enforced by RLS, not application logic).

Running the backend now requires `ZONARYOS_DATABASE_URL` (the `zonaryos_app` DSN), `ZONARYOS_OIDC_ISSUER_URL` (e.g. `http://localhost:8081/realms/zonaryos`), and `ZONARYOS_OIDC_CLIENT_ID` (default `zonaryos-web`) - see `.env.example`. `ZONARYOS_PLATFORM_ADMIN_EMAILS` (comma-separated, optional, empty by default) is the platform-admin allowlist - see the "Platform Admin" section below.

### Frontend: login flow

`web/src/app/api/auth/{login,callback,logout}` implement Authorization Code + PKCE directly against Keycloak (no auth framework dependency, to avoid pulling in one of uncertain compatibility with this Next.js version for what's still a minimal proof of the flow): `/api/auth/login` redirects to Keycloak with a PKCE challenge and `state`, stored in short-lived httpOnly cookies; `/api/auth/callback` validates `state`, exchanges the code for a token, and stores the access token in an httpOnly `zonaryos_session` cookie (never readable by client-side JS) and the refresh token in a second httpOnly `zonaryos_refresh_token` cookie (see "Session refresh" below). `web/src/app/api/me/route.ts` and the homepage forward the access token as a Bearer token to the Go backend's `/api/me`. Requires `ZONARYOS_KEYCLOAK_ISSUER_URL` and `ZONARYOS_KEYCLOAK_CLIENT_ID` in `web/.env.local` (see `web/.env.example`).

### Session refresh

Keycloak's default realm settings apply here (`deploy/keycloak/zonaryos-realm.json` sets none of `accessTokenLifespan`/`ssoSessionIdleTimeout`/`ssoSessionMaxLifespan` explicitly): an access token is only valid for **5 minutes** (`accessTokenLifespan`), the SSO session (and therefore the refresh token tied to it, since nothing here uses offline access) goes stale after **30 minutes of no activity** (`ssoSessionIdleTimeout`), and the whole session is force-ended after **10 hours** regardless of activity (`ssoSessionMaxLifespan`) - these are Keycloak 26.0's (the version `docker-compose.yml` pins) own built-in defaults, not something this repo configures. Before this mechanism existed (Open Points item 41), the `zonaryos_session` cookie's `maxAge` was set to the access token's own ~5 minute lifespan with nothing else - every user was silently logged out roughly 5 minutes after login, well inside a normal session.

The fix is `web/src/proxy.ts` (Next.js 16's renamed `middleware.ts` - see its own matcher/history note in the file), not a wrapper around the per-endpoint fetch helpers in `web/src/lib/*.ts`. Two reasons, documented in full in `proxy.ts`'s own comment: (1) React Server Components (every page under `app/[locale]` that calls `requireFirmContext`) can read cookies during render but cannot *write* them - only a Route Handler, Server Action, or the proxy itself can set a `Set-Cookie` header, and the proxy is the one place that runs before both page renders and API routes; (2) 17 of the `app/api/*/route.ts` handlers already read `zonaryos_session` directly off `request.cookies` with no shared chokepoint to retrofit - doing the refresh once in the proxy meant zero changes were needed to any of `lib/*.ts`'s fetch helpers or the routes/pages that call them.

On every request except the auth routes themselves (`/api/auth/*`), the proxy decodes the access token's `exp` claim (no signature verification needed - the Go backend already verifies it on every request the cookie is forwarded to) and, if it's missing or within 30 seconds of expiring, calls Keycloak's token endpoint with `grant_type=refresh_token` (`web/src/lib/session.ts`'s `refreshAccessToken`, the same endpoint `callback/route.ts` already calls with `grant_type=authorization_code`). On success, both cookies are rewritten on the *request* (so anything downstream in the same request-Server Component or Route Handler-sees the new token immediately) and set on the *response* (so the browser gets fresh cookies for next time). On failure - the refresh token itself has actually expired or was revoked, i.e. the terminal case the idle/max-lifespan timeouts above describe - both cookies are cleared and the request falls through unauthenticated, into the exact same "no valid session" path every page/route already had (redirect to `/${locale}` for pages, 401 for API routes) - no change needed there, no loop, no confusing error. `web/src/app/api/auth/logout/route.ts` also now calls Keycloak's `/protocol/openid-connect/logout` endpoint to revoke the refresh token server-side before clearing both cookies.

`scripts/e2e_smoke_test.sh`'s "session refresh" section is the real proof: rather than a full, honest 5-minute `sleep` (impractical for a CI job that otherwise runs in under a minute), it uses Keycloak's Admin REST API (`KC_BOOTSTRAP_ADMIN_USERNAME`/`PASSWORD`, already set by `docker-compose.yml`'s dev Keycloak container) to temporarily override the realm's `accessTokenLifespan` to 5 seconds, gets a real token under that override, genuinely sleeps past its real expiry, confirms the backend rejects that token directly (proving it's actually expired, not a fake test), then hits the frontend with it and confirms both a 200 response and a brand-new `zonaryos_session` cookie that the backend accepts directly - proving the refresh is real, not "login works then immediately calls again." It also revokes the refresh token and confirms the terminal path (a clean redirect with cleared cookies, not a loop). The realm override is restored via a `trap` before the script exits either way.

## Running the full stack in containers

See `docs/OPEN_POINTS.md` item 34 for the deployment-target investigation this came out of. This section covers what actually exists today: a containerized backend + frontend, a local docker-compose stack that runs the whole thing (Postgres, Keycloak, backend, frontend) together, and (if/when the Developer provisions real Oracle access) a near-term dev/test deployment target. **None of this is a production commitment** - see the caveats below.

### Building the images

`Dockerfile` (backend, builds both `cmd/server` and `cmd/migrate`) and `web/Dockerfile` (frontend, Next.js standalone output) are both multi-stage and use only portable, multi-arch base images (`golang`, `node:22-alpine`, `gcr.io/distroless/static-debian12`) - nothing Oracle- or any other cloud-specific. Build for the current machine's architecture with:

```
docker compose build
```

or cross-build for the Oracle Ampere A1 target (arm64) explicitly:

```
docker buildx build --platform linux/arm64 -t zonaryos-backend:arm64 .
docker buildx build --platform linux/arm64 -t zonaryos-frontend:arm64 -f web/Dockerfile .
```

**Verify the architecture, don't assume it.** The backend `Dockerfile` cross-compiles Go (`CGO_ENABLED=0`, `GOOS`/`GOARCH` from Docker's `TARGETOS`/`TARGETARCH` build args) rather than needing to execute arm64 code during the build - but this only works correctly if `buildx` actually populates `TARGETARCH` for the requested `--platform`. Verified during this work: the plain default `docker` buildx driver silently produced an image whose manifest said `linux/arm64` but whose binary inside was still `x86-64` (`TARGETARCH` wasn't propagated) - a real, not hypothetical, failure mode. Use a `docker-container` driver builder (`docker buildx create --driver docker-container --use`) and confirm the output before trusting it:

```
docker create --name check <image> && docker cp check:/usr/local/bin/server /tmp/server-check && docker rm check
file /tmp/server-check   # must say "ELF 64-bit LSB executable, ARM aarch64" for the arm64 build
```

### Running the full stack locally

```
docker compose up -d
```

This builds and starts Postgres, Keycloak, a one-shot `migrate` service (applies migrations, then exits - `backend` waits for it via `depends_on: condition: service_completed_successfully`), the backend, and the frontend. Every service uses `network_mode: host` **deliberately**, not as a shortcut: the frontend's OIDC login flow (`web/src/app/api/auth/login` and `.../callback`) needs one issuer URL reachable both by the end user's real browser and by the frontend container's own server-side token exchange, and Keycloak's `start-dev` mode derives each issued token's `iss` claim from whichever host:port actually requested it - bridge-network service names (e.g. `keycloak:8080`) would be unreachable from a real browser. Host networking keeps every service reachable at `localhost:<port>` from every other service *and* the browser, matching the exact assumption every existing manual/CI E2E verification already made (`scripts/e2e_smoke_test.sh`, the CI E2E job) - so no env var values differ from the non-containerized `.env`/`web/.env.local` setup already documented above, **except Postgres's port**: this compose file's `postgres` service listens on `5433`, not Postgres's default `5432` - a real deploy target turned out to already run its own native (non-Docker) PostgreSQL on `5432`, and since host networking means Docker's `ports:` publishing doesn't apply (there's no bridge network to remap - the server process itself has to be told to listen elsewhere, which `command: ["postgres", "-p", "5433"]` on the `postgres` service does), the exact same collision could just as easily happen on a developer's own machine if it already runs a local Postgres. Because `make dev-up` (`docker compose up -d`, i.e. this file) is this repo's default/primary way to get "a real Postgres" for the test suites below, **every `ZONARYOS_TEST_*_DATABASE_URL`/`.env.example` connection string in this document now points at `5433` to match** - the one exception is `make dev-up-standalone`'s native system Postgres (see "Fallback: no Docker registry access" below), which is unaffected by any of this and stays on the OS's actual `5432`.

First boot: the backend's `identity.NewVerifier` discovers Keycloak's OIDC config at startup and fails fast if Keycloak isn't ready yet (`cmd/server/main.go` doesn't retry) - `backend` is configured `restart: on-failure:10` to ride out that race rather than needing a bespoke wait-for-it script. A few restarts on first `docker compose up` are expected, not a bug.

**A real, non-hypothetical bug found and fixed while proving this end-to-end**: Next.js's standalone-mode `server.js` always builds `request.url` from its own bind hostname (`HOSTNAME` env, defaulting to `0.0.0.0`), never from the incoming request's actual `Host` header - a known Next.js standalone-server limitation (`experimental.trustHostHeader` does not override it, since `server.js` unconditionally passes its own hostname to the server constructor). This broke the OAuth `redirect_uri` the login/callback/logout routes built via `new URL(path, request.url)` - it came out as `http://0.0.0.0:3000/...`, which Keycloak's registered client (`http://localhost:3000/*`) rejects. Fixed in `web/src/lib/requestOrigin.ts`, used by all three `web/src/app/api/auth/*` routes: builds the origin from the request's `Host`/`X-Forwarded-Host` header instead of `request.url`. Verified with a full interactive PKCE round-trip (not just the Direct Access Grant `scripts/e2e_smoke_test.sh` normally uses) against the containerized stack: real Keycloak login form submission -> real authorization code -> real token exchange -> correct `redirect_uri` -> session cookie set -> homepage rendered.

Verifying the stack works: `./scripts/e2e_smoke_test.sh` against the containerized services (same script CI already runs against the non-containerized ones):

```
BACKEND_URL=http://localhost:8080 FRONTEND_URL=http://localhost:3000 \
KEYCLOAK_ISSUER_URL=http://localhost:8081/realms/zonaryos ./scripts/e2e_smoke_test.sh
```

`docker compose down` stops and removes the containers (add `-v` to also drop the Postgres volume).

### Deploying to Oracle Cloud Always Free (near-term dev/test target only)

Per the item 34 interim decision: an Oracle Always Free Ampere A1 instance (currently 2 OCPU/12GB, arm64) is a **near-term dev/test deployment target, not a production commitment**. Nothing in `Dockerfile`, `web/Dockerfile`, or `docker-compose.yml` is Oracle-specific - the same artifacts run on any plain Linux host with Docker (a DigitalOcean droplet, a bare-metal box, etc.) with no changes.

**Provisioning is done**: the instance exists (`zonaryos.duckdns.org`, a shared box also running unrelated live services behind nginx), and a dedicated deploy SSH key is in place. **The real reverse-proxy deployment (making the stack reachable at `https://zonaryos.duckdns.org` instead of `localhost`, alongside those other sites) is a separate, more involved concern than just `docker compose up -d` - see `docs/DEPLOYMENT.md` for the full command-by-command sequence, the `docker-compose.prod.yml` overlay, and `deploy/nginx/zonaryos.conf`.** That document also covers the Oracle Cloud Security List (firewall) rules needed - only 443/80 open publicly, Postgres/backend/Keycloak's raw port never exposed.

**Caveats - so this is never mistaken for a production environment (see `docs/OPEN_POINTS.md` item 34):**
- **No SLA.** Always Free is a best-effort tier with no uptime guarantee.
- **No automatic backup.** The Postgres data volume lives only on that one instance's disk; nothing here schedules snapshots or off-instance backups.
- **Single region, single instance.** This does not implement Vision §4's active-passive/multi-region topology - it is one Postgres, one Keycloak, one backend, one frontend, all on one host.
- **Oracle can reclaim Always Free resources under capacity pressure.** The instance is not guaranteed to stay up or keep its allocation indefinitely.

None of this blocks using the instance for dev/test purposes - it just means nothing here should be pointed to by real customer data or treated as the answer to item 34's actual production deployment-target question, which remains open pending the Developer's decision (see item 34's open questions).

## Database schema and Row-Level Security

Migrations live in `migrations/*.sql` (embedded into the binary via `migrations/embed.go`) and are applied with:

```
make migrate    # runs `cmd/migrate`, using ZONARYOS_MIGRATE_DATABASE_URL
```

`ZONARYOS_MIGRATE_DATABASE_URL` must point at a privileged/owner role (the docker-compose Postgres superuser). The migration also creates an unprivileged `zonaryos_app` login role — this is the role the *application* connects as, and the only role RLS policies actually restrict (the owner/superuser bypasses RLS by design, so migrations must never run as the same role the server uses).

Every tenant-scoped table (`roles`, `role_permissions`, `user_firm_roles`) has Row-Level Security enabled, keyed off the `app.current_firm_id` Postgres session setting. Application code must only touch these tables through `internal/platform/db.WithFirmContext`, which sets that context per transaction — never via a manual `firm_id = ?` filter instead (Never-Violate Rule 3). `firms` and `users` are global (not firm-scoped) tables: a user can belong to several firms via `user_firm_roles`.

### Authorization checklist for new endpoints

**`WithFirmContext`'s RLS scoping is not a membership check.** It confines a query to rows whose `firm_id` matches whatever `firmID` value the caller passed in — nothing more. If that `firmID` came from a URL path, query parameter, or request body (i.e. from the caller, not derived from something already proven to belong to them), RLS alone lets any authenticated user read or write that firm's data just by supplying its real ID. This was a real, exploitable bug (found via PR #6's own end-to-end verification, not by design) in `CurrentState`, `ListInstances`, and `LookupDefinitionByKey`, and a milder existence-oracle variant in `CreateInstance`/`ExecuteTransition` — all now fixed. See Open Points item 37 for the full audit.

Before adding any function or HTTP handler that accepts a firm-scoping ID (`firmID` today; watch for the same shape on any future tenant-scoping identifier) from the caller:

1. **Does it read or write a firm-scoped table at all?** If not (e.g. it only touches the global `firms`/`users`/`permissions` tables), this checklist doesn't apply.
2. **Is the membership check already implied?** `internal/permission.Has(ctx, tx, firmID, userID, permissionKey)` requires a real `user_firm_roles` row for `(userID, firmID)` to return `true` — a function that only proceeds when `Has` succeeds is already protected, no separate check needed (`CreateInstance`'s and `ExecuteTransition`'s actual state mutations are covered this way).
3. **If not, call `internal/permission.IsMember(ctx, tx, firmID, userID)` first** — before the first `SELECT`/`INSERT`/`UPDATE` against any firm-scoped table, inside the same `WithFirmContext` transaction, not after. `CurrentState`/`ListInstances`/`LookupDefinitionByKey` are the reference examples.
4. **Prefer the same error for "doesn't exist" and "you're not a member."** `writeEngineError`'s convention (404 either way) means a non-member can't distinguish a firm/instance/definition that's genuinely missing from one that's real but not theirs — don't leak that distinction with a different status code or message.
5. **Write the regression test as a real cross-tenant attempt**, not just a mismatched-context one: seed two firms, a real user who is a member of firm B only, and assert that supplying firm A's genuine ID gets rejected — a test that only checks "wrong context, made-up ID" would not have caught the original bug (see `TestRLS_InstanceIsNotVisibleFromAnotherFirm`'s `firmA`-with-`userB` case, and `TestCreateInstance_NonMemberGetsNotFoundNotPermissionDenied`/`TestExecuteTransition_NonMemberGetsNotFoundNotPermissionDenied`, for the pattern).
6. **Verify live, not just via the Go test suite**, before calling it done: start the real server (a stale `go run` background process can otherwise make you think a fix didn't take, or did, when it's testing old code — rebuild explicitly and confirm the PID/port), create two real firms through the actual wizard flow, and `curl` the cross-tenant attempt with a real bearer token.

## Workflow engine

`internal/workflow` implements Vision §3's "graph-based state machine": a business process is a set of rows (`workflow_definitions`, `workflow_states`, `workflow_transitions`) rather than Go code written per workflow - a 7-step manufacturing flow is just a bigger `DefinitionSpec` value passed to `DefineWorkflow`, not a new code path.

- **`DefineWorkflow`** validates a `DefinitionSpec` (exactly one initial state, no dangling state references, unique (from-state, action) pairs) and writes it as rows in one `WithFirmContext` transaction, upserting any permission keys it references into the global `permissions` catalog from `migrations/0001_core_schema.up.sql` along the way - reusing that catalog is the Never-Violate Rule 7 "permission tag" mechanism, not a new one. It's a thin wrapper around **`DefineWorkflowTx`**, the same logic against an already-open transaction, for callers that need workflow provisioning to be one step inside a larger atomic operation.
- **Self-action auto-grant**: `DefineWorkflowTx` takes a `granteeRoleID` - when a firm's own action provisions a new permission key (here, by defining a workflow), that permission is granted to the role that triggered the action, in the same transaction, instead of being left as a separate step every caller has to remember. Pass `uuid.Nil` to skip granting - what the pool-based `DefineWorkflow`/`SeedStockToSaleWorkflow` do, since those exist for fixtures/tests that only want a workflow's shape to exist, not a real grant against a real acting role (several workflow-engine tests deliberately seed a role with nothing granted, to test permission enforcement - auto-granting through those entry points would break that). There is no other kind of permission bypass anywhere in this system: an "owner" role (see the wizard section below) holds what it holds because of real, auditable `role_permissions` rows this mechanism wrote, never an implicit superuser check.
- **`internal/permission.Has`** is the one place a permission check happens: does the caller hold `permissionKey` through any role assigned to them in this firm. Any future module gating an action behind a permission should use this, not a bespoke check.
- **`internal/permission.IsMember`** reports whether the caller belongs to `firmID` *at all*, through any role. This exists because `WithFirmContext`'s RLS scoping alone is not a membership check: it confines a query to rows whose `firm_id` matches whatever ID the caller passed in, which is trivially satisfiable by any authenticated user who simply supplies a real firm ID that isn't their own. `Has` already carries this guarantee implicitly (its `user_firm_roles` join returns nothing for a non-member), but the read-only functions below originally had no equivalent check - a real cross-firm data leak, found and closed while building the stock list feature (see `TestRLS_InstanceIsNotVisibleFromAnotherFirm` and the sibling `_RLS` tests for `ListInstances`/`LookupDefinitionByKey`, which include the exact non-member-supplies-a-real-ID regression). Every function below now checks it before returning anything.
- **`CreateInstance`** starts a new instance in a definition's initial state, gated by the definition's `create_permission_key`. This is "add stock" in this PR's concrete workflow - modeled as instance creation, not a transition (creation has no from-state), but enforced and audited identically to one. `permission.Has` already implies membership for the actual write, but `CreateInstance` also checks `IsMember` first, before its own `workflow_definitions` lookup - the Open Points item 37 audit found that lookup let a non-member learn a definition existed (via a 403 instead of a 404) before being denied; a minor metadata oracle, not a data leak, but closed for consistency with every other function here.
- **Payload schema (Open Points item 35, extended by item 38)**: `DefinitionSpec` carries an OPTIONAL `Fields []FieldSpec` (`spec.go`) - each a `{Name, Type, Required}`, plus three type-scoped extras item 38 added: `Options []string` (only for `Type == "enum"`), `ReferenceDefinitionKey string` (only for `Type == "reference"`), and `ArrayItemType string` (only for `Type == "array"`, itself restricted to one of the four original scalar types). `Type` is one of `string`/`number`/`boolean`/`date`/`enum`/`reference`/`array`. Nil/empty `Fields` (every `DefinitionSpec` from before item 35, `StockToSaleSpec`/`CustomerPipelineSpec` included) means exactly today's behavior: `Validate()` requires nothing new, `CreateInstance` accepts any payload it already did. When `Fields` is set, `CreateInstance` validates the incoming payload against it before writing anything - every required field present, and a type check of whatever's present (`validatePayload`/`checkFieldType`/`checkScalarValue`, `engine.go`) - rejecting with `ErrPayloadValidation` (400 via `writeEngineError`) on failure. This is a create-time-only gate: `CurrentState`/`ListInstances`/`ExecuteTransition` never consult a schema, so adding one to a definition after instances already exist can never invalidate an existing row - only new `CreateInstance` calls going forward are affected. Persisted as a nullable `jsonb` column, `workflow_definitions.payload_schema` (`migrations/0005_workflow_payload_schema.up.sql`) - item 38's three new field-shape properties needed **no migration**: the column has no fixed shape (a plain `jsonb`), so `payloadFieldRow`'s three new `omitempty` JSON keys just aren't present on any pre-item-38 row, and `unmarshalPayloadSchema` leaves them at their zero value for those. `StockToSaleSpec`/`CustomerPipelineSpec` were deliberately **not** retrofitted with any of item 35's or item 38's field types: several of this package's own tests create instances of both with only a subset of their "real" fields (e.g. `CreateInstance` with just `{"item": "widget"}`, no `quantity`; `{"name": "Acme Inc"}`, no `contact`) - any new required field would break those. Both items' mechanisms are instead proven end-to-end by dedicated test-only definitions (`internal/workflow/payload_schema_test.go` for item 35's four scalar types, `internal/workflow/payload_schema_type_test.go` for item 38's enum/reference/array), the same role the test-only schema-less `purchase_order` definition already plays for freeform behavior in `scripts/e2e_smoke_test.sh`. `DefineWorkflowForFirm`'s builder (below) also accepts this OPTIONAL `fields` list, unchanged for a caller that never sets it.
  - **`enum`**: the field's value must be a string present in `Options`. `Validate()` rejects an enum field with zero options, an empty-string option, or a duplicate option.
  - **`reference`**: the field's value must be a UUID string identifying an existing `workflow_instances` row, belonging to the definition named by `ReferenceDefinitionKey`, IN THE SAME FIRM (`checkReferenceField`, `engine.go`) - a value that doesn't resolve, or resolves to another firm's instance, is rejected identically (no metadata leak about what exists elsewhere). This check is a real database query inside `CreateInstance`'s own transaction (not a separate connection), and takes a `FOR SHARE OF wi` row lock on the referenced instance for the rest of that transaction - defensive design, not a response to a reachable bug: as of this batch there is still no delete path anywhere for `workflow_instances` (no `DELETE FROM workflow_instances`, no `DeleteInstance`), so the "referenced row deleted between check and write" race this lock guards against cannot happen today. If a delete path is ever added, a concurrent `DELETE` would need its own row lock and would simply block until this transaction commits/rolls back, rather than being able to remove a row a reference was just validated against - one query-level lock modifier, not bespoke locking machinery, sized to a threat that doesn't exist yet. `ReferenceDefinitionKey` naming a REAL definition for the firm can't be checked by `Validate()` itself (it's a pure, DB-free function with no firm context) - that check lives in `DefineWorkflowTx` instead (shared by every path that can define a workflow: fixtures, the wizard, and the HTTP-reachable `DefineWorkflowForFirm`), which does have a live transaction/firmID, and rejects an unresolvable key with `ErrInvalidSpec`.
  - **`array`**: the field's value must be a JSON array where every element passes `ArrayItemType`'s own scalar check (`checkScalarValue`, shared with the plain-scalar-field code path). `ArrayItemType` is restricted to `string`/`number`/`boolean`/`date` - `Validate()` rejects `enum`/`reference`/`array` itself as an `ArrayItemType` (no nested arrays, no arrays of enums/references) at spec-definition time, not silently at runtime.
- **`ExecuteTransition`** moves an instance along an edge in the graph (e.g. "record a sale"), gated by that transition's own `permission_key`, all inside one `WithFirmContext` transaction so the permission check and the state mutation can't race. Same `IsMember`-first treatment as `CreateInstance`, for the same reason (its `workflow_instances`/`workflow_transitions` lookups otherwise ran before the implied-by-`Has` membership check).
- Every `CreateInstance`/`ExecuteTransition` call writes exactly one row to `audit_log` - a general-purpose, not workflow-specific, data-change audit trail (Vision §3; view/read-level logging is future work). The workflow engine is this table's first writer; later modules (inventory, sales, ...) are expected to write to the same table, not invent their own.
- **`stock_to_sale.go`** is the concrete first instance: `in_stock` (initial) → `sold` (terminal) via the one transition `record_sale`. `SeedStockToSaleWorkflow(ctx, pool, firmID)` instantiates it for a firm - called by the firm-creation wizard (see below) for every new firm. Its instance payload convention (not an engine-level concept - `payload` is opaque `jsonb` to the engine) is `{"item": "<name>", "quantity": <number>}` at creation time, established by the stock UI (`web/src/app/[locale]/stock`) and its tests; a future workflow could use an entirely different payload shape without touching the engine.
- **`CurrentState`** and **`ListInstances`** (the latter lists instances of one definition within a firm - the stock list page's data source) both now take `userID` and check `permission.IsMember` before reading anything. Neither is filtered by the caller's own *permissions* though - available actions are listed regardless of whether the caller could actually execute them; that enforcement happens at `ExecuteTransition` time, same as before. `ListInstances` also takes a `ListInstancesOptions{Limit, Offset, Search}` - the zero value returns every instance unfiltered (its original, and still default, behavior - so `WorkflowHistory`'s own correlation fetch and every pre-existing caller keep working unchanged), but a caller can page (`Limit`/`Offset`, capped at 200 via the HTTP handler) and/or text-filter (`Search`, matched case-insensitively against the instance's current state key/name and its raw payload text - generic across any definition's payload shape, not a hardcoded field) explicitly. `ListInstancesResult.Total` reports the filtered-but-unpaged count (via one `COUNT(*) OVER()` alongside the paged rows, not a second query) so a caller can render "page X of Y".
- **`LookupDefinitionByKey`** resolves a well-known key (e.g. `stock_to_sale`, see `StockToSaleKey`) to its firm-scoped `workflow_definitions` row, for callers that only know the key, not the UUID - also `IsMember`-checked.
- **`ListDefinitions`** lists every `workflow_definitions` row for a firm, ordered by name - the data source for the frontend's firm-level "Workflows" view (see the Application Frontend section below): a firm's second, third, ... workflow definition shows up there automatically, without a hardcoded frontend card per known workflow. Same `IsMember`-first treatment as every other read here.
- **`InstanceCountsByDefinition`** is the dashboard overview's data source (a later batch): for every workflow definition in a firm, how many instances currently sit in each state - one grouped `COUNT(*) ... GROUP BY` query with a `LEFT JOIN` from `workflow_states` out to `workflow_instances`, so a state with zero instances still reports an explicit `0` rather than being omitted, computed server-side instead of the frontend fetching every instance and counting client-side. Same `IsMember`-first treatment as every other read here.
- **`customer_pipeline.go`** is a second concrete workflow (a later batch), demonstrating the engine on a structurally different, relationship-shaped process rather than an inventory one: `lead` (initial) → `qualified` → `customer` (terminal) via `qualify`/`convert`, plus `mark_lost` reachable from *both* `lead` and `qualified` (two `TransitionSpec` rows sharing an action key and permission key but differing in from-state - proof `Validate`'s duplicate-transition check keys on the (from-state, action) pair, not the action alone). `SeedCustomerPipelineWorkflow(Tx)` mirrors `SeedStockToSaleWorkflow(Tx)` exactly. Like `stock_to_sale`, it has no payload schema of its own (a deliberate choice - see the payload schema bullet above) - `CreateInstanceForm`'s free-form editor works for a lead's fields the same as it does for stock's.
- **`AvailableAction.PermissionKey`**: `CurrentState` and `ListInstances` both include the permission key each listed action is actually gated by, so a UI rendering an action button can carry the real Never-Violate Rule 7 permission tag instead of a hardcoded duplicate of the constant `ExecuteTransition` checks. `AvailableAction.Name` and `DefinitionInfo.CreatePermissionKey` (workflow_transitions.name / workflow_definitions.create_permission_key) exist for the same reason on the frontend's generic action buttons and "create instance" form - see the Application Frontend section.
- **`DefineWorkflowForFirm`** is `DefineWorkflow`'s HTTP-reachable counterpart - the actual point of this batch of work: until now, defining a new workflow was only reachable from Go fixtures (`SeedStockToSaleWorkflow`) or the firm-creation wizard, never by a firm itself. Owner-gated (`permission.IsMember` then `IsOwner`, same order every owner-gated function in this codebase checks) - defining a new workflow type is a structural firm decision, the same tier as firm creation itself. On success, the acting owner's own owner-flagged role is looked up and passed as `DefineWorkflowTx`'s `granteeRoleID` (the self-action auto-grant above), so the firm isn't left holding a workflow nobody can use yet. `spec.Validate()` failures map to `ErrInvalidSpec` (400); a `(firm_id, key)` collision (Postgres `23505`, caught via `pgconn.PgError`) maps to `ErrDefinitionKeyExists` (409) - both real 4xx responses, not a generic 500. This is strictly the state-machine definition mechanism (states/transitions/permission keys) - it has no conditional-logic concept of its own; that's the separate Rule Engine, `internal/workflow/rules.go` - see the "Rule engine" section below.

HTTP surface (mirrors `internal/identity`'s `/api/me/firms/{firmID}/...` path-scoping - see `docs/api/openapi.yaml` for full request/response shapes):

- `GET /api/firms/{firmID}/workflow-definitions` — with `?key={key}`, resolve a well-known workflow key to its definition ID; without it, list every workflow definition the firm has (`ListDefinitions`) - two modes on one path, dispatched by the query parameter's presence rather than a second route, since a path-segment variant collides with the sibling `{definitionID}/instances` pattern below at `net/http` `ServeMux` startup
- `POST /api/firms/{firmID}/workflow-definitions` — define a new workflow for the firm (`DefineWorkflowForFirm`, owner-only)
- `POST /api/firms/{firmID}/workflow-definitions/{definitionID}/instances` — start an instance ("add stock", or the equivalent "create" action for any other workflow definition)
- `GET /api/firms/{firmID}/workflow-definitions/{definitionID}/instances` — list instances of a definition (the stock list, or any other workflow's instance list); optional `?limit=`/`?offset=` page through results (omit both for the old "everything" behavior) and `?q=` text-filters by state/payload content - the total matching count is reported via the `X-Total-Count` response header, not the body, so the body's array shape stays unchanged for any existing caller (see `docs/api/openapi.yaml`)
- `GET /api/firms/{firmID}/workflow-instances/{instanceID}` — read current state and structurally available next actions (membership-checked; not filtered by the caller's own permissions - enforcement happens when a transition is actually executed)
- `POST /api/firms/{firmID}/workflow-instances/{instanceID}/transitions/{actionKey}` — execute a transition ("record a sale", or any other transition on any workflow)
- `GET /api/firms/{firmID}/workflow-instance-counts` — the dashboard overview's data source (a later batch): every workflow definition the firm has, each with its instance count broken down by state (`InstanceCountsByDefinition`). A separate top-level path rather than nested under `/workflow-definitions`, since it aggregates across every definition at once instead of being scoped to one `{definitionID}` - additive-only, no existing route's shape changed (Never-Violate Rule 6)
- `GET /api/firms/{firmID}/workflow-definitions/{definitionKey}/rules` — lists every `workflow_rules` row for that definition key (see the "Rule engine" section below); membership-checked only, no rule-specific permission tier
- `POST /api/firms/{firmID}/workflow-definitions/{definitionKey}/rules` — create a rule (owner-only, `CreateRuleForFirm`)
- `PATCH /api/firms/{firmID}/workflow-definitions/{definitionKey}/rules/{ruleID}` — partially update a rule's name/enabled/autonomous/condition tree/actions (owner-only, `UpdateRuleForFirm`)
- `DELETE /api/firms/{firmID}/workflow-definitions/{definitionKey}/rules/{ruleID}` — delete a rule (owner-only, `DeleteRuleForFirm`)

## Rule engine

`internal/workflow/rules.go` implements Vision §3's "Autonomous Decision Layer" (Open Points item 7, decided together with item 12's wizard content since rules are also defined through the wizard eventually): unlimited-depth parametric "if this condition occurs -> automatically do this action" rules attached to a workflow definition, deterministic and no-ML per the vision. Storage is `workflow_rules` (`migrations/0008_workflow_rules.up.sql`) - firm-scoped, mandatory RLS (Rule 3), with a composite `FOREIGN KEY (firm_id, definition_key) REFERENCES workflow_definitions (firm_id, key)` so a rule can never reference a workflow definition that doesn't exist for its own firm.

- **`ExpressionNode`** is a rule's condition tree: either a **logic node** (`Op` one of `"and"`/`"or"`/`"not"`, `Children []ExpressionNode`) or a **condition leaf** (`Type` set, discriminating the fields below). A flat Go struct with `omitempty` type-specific fields, not a Go interface with per-kind implementations - the same shape `FieldSpec` (spec.go, item 38) already uses, so it round-trips through the `condition_tree` jsonb column with plain `encoding/json`, no custom (un)marshaling. Three leaf types:
  - **`field`** (`ConditionField`): `{field, op, value}` - compares a field from the triggering instance's own payload against a literal.
  - **`state`** (`ConditionState`): `{definitionKey, instanceIdField, state}` - the cross-workflow condition Vision §3 explicitly calls for: resolves `instanceIdField` from this instance's payload (expected to be a `reference`-type field, per item 38, pointing at another definition), looks up *that* instance's current state via a real Postgres read (`WithFirmContext`, not a mock), and checks it equals `state`.
  - **`field_compare`** (`ConditionFieldCompare`): `{fieldA, op, fieldB}` - compares two fields from the same instance's own payload against each other.
  - `op` is shared by all three roles above (a logic node's boolean operator, or a leaf's comparison operator: `eq`/`neq`/`lt`/`gt`/`lte`/`gte`, plus `contains` for `field` only) - unambiguous from context, exactly the wire shape the design brief specifies.
- **`Evaluate(ctx, tree, EvalContext) (bool, error)`** is the engine's pure entry point - no side effects of its own (a `state` leaf still performs a read via `EvalContext.Pool`, but never writes). `and`/`or` short-circuit; `not` requires exactly one child. **Fail-closed**: any leaf that can't be evaluated (a missing payload field, an unresolvable cross-workflow reference, a non-numeric value for `lt`/`gt`/...) returns `ErrConditionEvaluation`, not a `false` result - the caller (`EvaluateRules`) treats an error and a real `false` completely differently (see below).
- **`Action`** (also a flat, `omitempty`-tagged struct, same jsonb-round-trip reasoning) is one entry in a rule's `Actions`, run in order once `ConditionTree` evaluates true: **`transition`** (`ActionTransition`) autonomously executes a named workflow transition via the real `ExecuteTransition` (no bypass of its own permission/state checks - the acting `userID` is the same one that triggered the rule); **`notify`** (`ActionNotify`) writes a structured `audit_log` entry, `channel` always `"audit_log"` this batch (email/push, Open Points item 17, stay deferred) - `messageTemplate`'s `{{fieldName}}` placeholders are substituted with the triggering instance's payload values (`renderMessageTemplate`, plain string substitution, not a templating engine - the input is firm-authored text, not code); **`set_field`** (`ActionSetField`) merges `{field: value}` into the instance's stored payload, the same jsonb `||` merge `ExecuteTransition` itself uses.
- **`EvaluateRules`** is the impure driver, wired into `CreateInstance`/`ExecuteTransition` (engine.go) at the very end, AFTER the triggering write has already committed - not nested inside the same transaction, which `zdb.WithFirmContext` gives no seam to inject into. This still satisfies the design brief's "synchronous, inline, no goroutines, no eventual consistency" requirement: the triggering call does not return to *its* caller until `EvaluateRules` itself returns; an `EvaluateRules` error is logged (`log.Printf`, `%q`-escaped per gosec G706), never propagated, since the triggering operation has already committed by that point - there is nothing left to roll back. For each enabled rule matching the firm/definition/trigger (`on_create`/`on_transition` - schedule-triggered rules stay deliberately unmodeled, see Open Points below): a condition error writes an `evaluation_error` `audit_log` entry (`entity_type` `"workflow_rule"`) and skips that rule's actions entirely (fail-closed, per the design brief); a real `false` match just moves on; a `true` match with `Autonomous: false` writes a `pending_approval` `audit_log` entry instead of running the actions (Never-Violate Rule 8 - see below); a `true` match with `Autonomous: true` runs the actions via `executeRuleActions`, and any action error is itself logged the same fail-closed way.
- **`Rule.Autonomous`** (`workflow_rules.autonomous`, default `false`) is this package's answer to Never-Violate Rule 8 ("every rule has an explicit autonomous/human-approval toggle set by the end user - never hardcoded to always-autonomous"): the design brief's own literal `Rule` schema didn't include this field, but the rule was added anyway since Rule 8 is non-negotiable. What's genuinely NOT built yet: an approval queue/UI to actually review and run a `pending_approval`-logged match - today that state is only visible as an `audit_log` entry, not an actionable queue (flagged in `docs/OPEN_POINTS.md`).
- **`CreateRule`** stores a validated `Rule` - the fixture/test entry point, not owner-gated and not reachable via any caller-supplied firmID (see its own doc comment). **`ListRulesForDefinition`** is the read side, `IsMember`-checked like every other read in this package - the data source for `GET .../workflow-definitions/{definitionKey}/rules`.
- **`purchase_order`**/**`task_approval`** (see the "Firm-creation wizard" section below) exist partly to give the rule engine's cross-workflow `state` condition a real second workflow to reference in tests, not only as wizard content.
- **Rule Engine Builder UI (a later batch)**: `CreateRuleForFirm`/`UpdateRuleForFirm`/`DeleteRuleForFirm` are the owner-gated, HTTP-reachable counterparts to `CreateRule` (`permission.IsMember` then `IsOwner`, same order as `DefineWorkflowForFirm`) - `POST`/`PATCH`/`DELETE .../workflow-definitions/{definitionKey}/rules(/{ruleID})` (handlers.go). Both structural validators are pure and DB-free (`ValidateExpressionTree`, `ValidateActions`, both mapping to `ErrInvalidRule` -> 400) plus one real-DB check this batch adds: `checkObviousSelfReferentialLoop` rejects an `on_transition`-triggered rule whose own `transition` action resolves to a literal self-loop transition (`from_state_id == to_state_id`) - a guaranteed immediate re-fire, since `EvaluateRules`' `on_transition` scope isn't keyed to which specific transition fired, ANY transition on the definition re-evaluates every enabled `on_transition` rule including this one. This is deliberately the narrow, statically-detectable case, not full arbitrary-graph cycle detection (a longer cycle through several rules/transitions isn't caught) - `EvaluateRules`' existing fail-closed behavior is this codebase's actual backstop for that broader case. `UpdateRuleForFirm` re-validates the FULL resulting rule after a partial `RuleUpdate` patch is applied, not just the changed fields. Every mutation writes one `audit_log` entry (`entity_type` `"workflow_rule"`, action `create`/`update`/`delete`).
- **Frontend (`web/src/components/Workflow/RuleBuilder.tsx`/`RuleList.tsx`)**: mounted on the generic `/workflows/[key]` page (`WorkflowDefinitionView.tsx`), gated the same way `DefinitionBuilder.tsx` is - `RuleList` is visible to any member (matching `ListRulesForDefinition`'s own membership-only gate), `RuleBuilder` and `RuleList`'s enable/disable/delete actions only render for an owner. `RuleBuilder`'s condition-tree editor (`ConditionNodeEditor`) is a recursive AND/OR/NOT + leaf editor over `ruleBuilderState.ts`'s `BuilderNode` tree, id-addressed immutable mutation helpers (`updateNodeById`/`removeNodeById`/`addChildToLogicNode`/`wrapNodeInGroup`) and a pure, independently-tested serialization step (`nodeToExpressionNode`/`actionRowToRuleAction`, `ruleBuilderState.test.ts`) that turns UI state into the `ExpressionNode`/`Action` wire shapes - the same "pure serialization function, tested apart from rendering" pattern `builderValidation.ts` already established for `DefinitionBuilder`. A `field`/`set_field` leaf's field-name dropdown and typed value input (text/number/checkbox/enum) come from the definition's own OPTIONAL payload schema (item 35/38) when one exists; a `transition` action's actionKey dropdown is populated from the union of `AvailableAction`s across the definition's currently-listed instances (the closest available proxy for "every transition this definition has," since no endpoint returns the full state graph independent of any instance - falls back to free text when empty); a `state` leaf's cross-workflow definitionKey dropdown reuses the same `existingDefinitionKeys` list `DefinitionBuilder`'s own reference-field picker already fetches.

## Financial management core

`internal/accounting` is Vision §3's accounting/finance foundation: a firm-scoped chart of accounts and a double-entry journal - the minimal, generic backbone every other module (inventory valuation, purchasing, payroll, ...) eventually posts to, not a full accounting suite. Storage is `accounts`/`journal_entries`/`journal_lines` (`migrations/0009_financial_management_core.up.sql`) - firm-scoped, mandatory RLS (Rule 3), plus a `journal_template jsonb` column added to the existing `workflow_transitions` table for the workflow-to-ledger bridge below.

- **The one invariant**: a posted journal entry's debit lines and credit lines must sum to the same total. Enforced in `PostJournalEntryTx` (journal.go), application-layer, inside the same transaction as the entry's own insert - not a database `CHECK`/trigger, since a cross-row-and-cross-table sum constraint is impractical to express as a plain Postgres `CHECK` and a trigger-based equivalent would duplicate logic this function already owns as the single write path into `journal_entries`/`journal_lines`. The check itself is computed by Postgres's own exact `numeric` arithmetic (`SUM(amount) FILTER (WHERE side = 'debit') - SUM(amount) FILTER (WHERE side = 'credit')`, cast to `text` and checked for "is this string all zeros" - `isZeroDecimal`) - never a Go float, anywhere in this package, for any total. `PostJournalEntryTx` is the one shared entry point every caller that can post a journal entry goes through - `PostJournalEntry` (the owner-gated manual-entry HTTP path) and `internal/workflow.ExecuteTransition` (the bridge, below) - the same "one shared Tx-level function, every caller goes through it" pattern `internal/workflow.DefineWorkflowTx` already established for workflow provisioning.
- **Chart-of-accounts seeding** (`seed.go`'s `SeedDefaultChartOfAccountsTx`): called once from inside `internal/wizard.CreateDefaultFirm`'s own transaction, parametrically from the wizard's existing `SeedSelection` answers (`Sells`/`PurchasesFromSuppliers` - not manufacturing, since the wizard's manufacturing branch is still a `NodePlaceholder` dead end with no answer to key off). Core accounts (Cash, Trade Receivables, Trade Payables, Owner Equity, Retained Earnings) are seeded for every firm; Inventory/Sales Revenue/Cost of Goods Sold when `Sells`; Inventory (again)/Accounts Payable/Purchase Expense when `PurchasesFromSuppliers`. **Inventory is deliberately seeded by both groups**, deduplicated by account code before insert (a firm answering yes to both would otherwise hit `accounts`' `UNIQUE (firm_id, code)` constraint) - a firm that purchases from suppliers without also selling products (e.g. buying materials/supplies, not resale goods) still needs somewhere to post received goods; without this, `purchase_order`'s `receive` transition (below) would hit `ErrAccountNotFound` the first time it ran for such a firm.
- **The workflow-to-ledger bridge** (`internal/workflow/spec.go`'s `TransitionSpec.Journal *JournalTemplate`): an OPTIONAL journal template a transition can carry - `Description` (`"{{field}}"` placeholders, substituted from the transition's merged instance payload) plus `Lines []LineTemplate{AccountCode, Side, AmountField}`. `AmountField` names one payload field, or two joined by `"*"` (e.g. `"quantity*unit_price"`) for the one payload-derived computation this bridge supports natively - the realistic shape of a sale/purchase amount. At `ExecuteTransition` time (engine.go), the template is resolved against the merged payload and posted via `PostJournalEntryTx` **inside the same transaction** as the state change itself - both commit together or neither does. If the named field(s) are simply absent from the payload, the whole template is skipped for that call (not an error) - deliberately non-breaking (Rule 6 in spirit) for any `ExecuteTransition` caller that predates a transition gaining a `JournalTemplate`, or that just doesn't supply the financially-relevant fields on a given call. A field that IS present but malformed (wrong type), or a posting failure once fields are present (unknown account code - structurally unreachable for an unbalanced-entry failure here, since this bridge always emits balanced lines by construction), fails the whole transition and rolls back the state change with it.
  - `stock_to_sale`'s `record_sale` transition is wired with a real example: DR Trade Receivables / CR Sales Revenue, `quantity*unit_price` (`unit_price` is this batch's addition to a payload that already conventionally carried `quantity`; both stay OPTIONAL fields, not required, so every pre-existing `record_sale` caller that never supplied them keeps working exactly as before, just without a posted entry).
  - `purchase_order`'s **`receive`** transition (Sent → Received) is wired the same way: DR Inventory / CR Trade Payables, `total_amount` - the point a real financial event actually happens (goods received, both a real asset and a real liability created at once - standard perpetual-inventory treatment for a purchase not yet paid). **`send`** (Draft → Sent) deliberately carries no `JournalTemplate`, contrary to an earlier draft of this design that proposed posting there too: sending a PO to a supplier is a commercial communication, not a completed transaction under accrual accounting (nothing has actually been received yet - posting there would expense before the matching receipt, violating the matching principle, and would double-count Trade Payables against `receive`'s own entry for the same purchase). `supplier_name`/`total_amount` are two new OPTIONAL fields on `PurchaseOrderSpec.Fields` (this workflow had no payload schema before this batch).
- **Manual journal entries**: `PostJournalEntry` (owner-gated) is `PostJournalEntryTx`'s pool-based, HTTP-reachable counterpart for a caller-authored entry, not derived from any workflow transition - `POST .../journal-entries`.
- **`GetAccountBalance`**: `SUM(debits) - SUM(credits)` or the reverse, depending on the account type's normal balance side (`AccountType.normalDebitBalance`, accounts.go) - computed by the same exact-arithmetic, cast-to-`text` convention as the balance check above.
- **Financial reports** (`reports.go`, computed views - no new tables, no stored report rows): **`GetProfitAndLoss`** sums every revenue account credit-minus-debit and every expense account debit-minus-credit over an optional `[from, to]` window (either bound may be nil), grouped by account, plus `NetIncome = TotalRevenue - TotalExpenses`. **`GetBalanceSheet`** sums asset accounts debit-minus-credit and liability/equity accounts credit-minus-debit, all up to an `asOf` instant. **`CurrentEarnings`** (net income accrued since the last close, folded into `TotalEquity`) exists because this batch has no period-closing mechanism - without folding unclosed revenue/expense into equity, `Assets = Liabilities + Equity` would show as permanently, structurally false the moment any firm posts its first sale (an asset increases with nothing on the liability/equity side), which would make the `Balanced` flag a permanent false alarm rather than a genuine signal. With `CurrentEarnings` folded in, `Balanced` staying `true` is the expected, correct state under normal operation - `Balanced: false` is then a real data-integrity signal, not an artifact of missing closing entries. Both totals and the balance check are computed via Postgres's own exact `numeric` arithmetic, same discipline as everywhere else in this package.
- **Authorization**: `IsMember` gates every read (`ListAccounts`, `GetAccountBalance`, `ListJournalEntries`, `GetProfitAndLoss`, `GetBalanceSheet`) - ordinary firm data visibility, the same tier as `internal/workflow.ListInstances`. `IsMember` then `IsOwner` gates every account/manual-entry mutation (`CreateAccount`, `UpdateAccount`, `PostJournalEntry`) - a structural firm-financial decision, the same tier as `DefineWorkflowForFirm`/`CreateRole`. `PostJournalEntryTx` itself makes no authorization decision (`ciaudit:ignore-firmid-check`, same reasoning as `DefineWorkflowTx`) - its callers (`PostJournalEntry`, `ExecuteTransition`) have already checked before reaching it.

HTTP surface (`internal/accounting/handlers.go`):

- `GET`/`POST /api/firms/{firmID}/accounts`, `PATCH /api/firms/{firmID}/accounts/{accountID}` (code/type immutable once created - only name/isActive), `GET /api/firms/{firmID}/accounts/{accountID}/balance`
- `GET`/`POST /api/firms/{firmID}/journal-entries` (`?limit=`/`?offset=` paging on the list, `X-Total-Count` header, same convention as the audit log/workflow-instances endpoints)
- `GET /api/firms/{firmID}/reports/pnl?from=&to=` (both optional, RFC3339), `GET /api/firms/{firmID}/reports/balance-sheet?as_of=` (optional RFC3339, defaults to now)

Frontend: `/settings/accounts` (owner-gated chart-of-accounts management, `components/Accounting/AccountsManager.tsx`), `/financials` (member-gated, three tabs - Account Balances, Profit & Loss with a from/to date range, Balance Sheet with an as-of date, both date pickers plain `<form method="get">`s driving URL search params, not client state, matching `WorkflowDefinitionView`'s own `?page=`/`?q=` convention), and a read-only journal-template section on the generic `/workflows/[key]` page for any transition that carries one. `components/Workflow/DefinitionBuilder.tsx` also gained a per-transition "Journal" expander (account code chosen from the firm's real chart of accounts via `/api/firms/{firmID}/accounts`, never free text) so an owner can attach a `JournalTemplate` to a transition they're defining through the UI, not just through Go-defined specs like `stock_to_sale`/`purchase_order`.

## HR core, task/project management, and the reporting foundation

`internal/hr` is Vision §3's minimal HR foundation: every business has people, so a firm-scoped record of who they are (employees/contractors/partners, `people`) and what contract terms they're under (`contracts`, append-only history per person) - not a payroll/time-tracking/performance-review system (see `migrations/0010_hr_core.up.sql`'s own scope-boundary comment). `people.custom_fields` (jsonb) gives firm-specific HR attributes without a schema change, the same "PostgreSQL + JSONB hybrid" principle `firms.attributes` already uses. `IsMember` gates every read (`ListPeople`, `GetPerson`, `ListContracts`); `IsMember` then `IsOwner` gates every write (`CreatePerson`, `UpdatePerson`, `CreateContract`) - the same tier as `internal/accounting`'s chart-of-accounts mutations. The dashboard's actual five KPIs (`kpiDescriptors`) are all instances of these four `Kind`s, referencing `internal/accounting`'s own exported account-code constants and `internal/workflow.TaskApprovalKey` - not five hand-written SQL queries. Adding a KPI that fits an existing `Kind` is a one-line addition to `kpiDescriptors`, not a new code path; only a genuinely new shape of aggregation needs a new `Kind` and its own compute function. Every total is computed by Postgres's own exact `numeric` arithmetic (`accountBalanceSum`), same discipline as `internal/accounting`'s own reports; an account/workflow/person-status with no data yet for a firm reads back as a real `0`, not an error.

- Frontend: `/reports` (a simple tile grid, `t("kpi." + result.key)` for each label).

## Firm-creation wizard

`internal/wizard` implements Vision §3's "Self-Configuring Infrastructure": a newly-authenticated Keycloak user with zero firm memberships (detected via `internal/identity.Memberships`, PR 3's firm-discovery mechanism) is routed into this wizard instead of the normal app.

- **`tree.go`** models the wizard as an actual decision tree, not a hardcoded form: a `Node` is either a question (with `Answers`, each pointing at the next `Node`), a terminal action, or a terminal placeholder. This batch (Open Points item 12) replaced the original single-question slice (`"do you manufacture?"` only) with the tree's real root question sequence, ordered per Vision §3's principle ("questions that unlock features almost every commercial business needs come first"): (1) `doYouSellProductsOrServices` - `"yes"` opens two sub-questions, `doYouTrackPhysicalInventory` and `doYouManageCustomerRelationships`, before continuing; `"no"` skips straight to question 2; (2) `doYouPurchaseFromSuppliers`, asked either way; (3) `doYouManageTasksOrApprovals`, asked either way (tasks/approvals are universal, not conditioned on selling); (4) `doYouManufacture` - `"no"` reaches the `create_default_firm` action, `"yes"` still dead-ends at the pre-existing `manufacturingComingSoon` placeholder (manufacturing support itself remains out of scope). `Node` fields carry i18n message keys (not literal text) for anything user-facing, matching Never-Violate Rule 4.
- **`SeedSelection`** (`tree.go`) is the accumulated yes/no answers from every workflow-gating root question (`Sells`/`TracksInventory`/`ManagesCRM`/`PurchasesFromSuppliers`/`ManagesTasks`). This wizard's HTTP surface is stateless request/response per node - there is no session carrying prior answers forward - so `SeedSelection` is NOT client-supplied round-tripped state: `buildTree` constructs every distinct path from `RootNode` to its own terminal `Node`, each carrying a `*SeedSelection` literal baked in at tree-construction time (`Node.Seed`, only set on the `create_default_firm` action node). The path taken to reach a terminal node *is* the record of every answer that led there.
- **`firm.go`**'s `CreateDefaultFirm` is the wizard's one implemented action, now parametric on `SeedSelection` (Open Points item 37's resolution: "Parametric New-Firm Workflow Seeding") instead of unconditionally seeding the same hardcoded pair for every firm: it creates the firm, a default `owner` role, the caller's membership in it, seeds the firm's starter chart of accounts (`accounting.SeedDefaultChartOfAccountsTx` - see the "Financial management core" section above), then seeds `workflow.StockToSaleSpec` only if `Sells && TracksInventory`, `workflow.CustomerPipelineSpec` only if `Sells && ManagesCRM`, `workflow.PurchaseOrderSpec` only if `PurchasesFromSuppliers`, and `workflow.TaskApprovalSpec` only if `ManagesTasks` - via `workflow.SeedStockToSaleWorkflowTx`/`SeedCustomerPipelineWorkflowTx`/`SeedPurchaseOrderWorkflowTx`/`SeedTaskApprovalWorkflowTx` (each reused as-is), all inside one hand-managed transaction. A firm whose answers ask for none of these still gets created, with zero seeded workflow definitions - the owner defines their own from scratch via `DefineWorkflowForFirm`, per item 37's resolution. `internal/platform/db.WithFirmContext` can't be used here since it needs a `firmID` up front and the firm doesn't exist yet; this function sets `app.current_firm_id` itself, once the new firm's ID is known, before touching any RLS-protected table - the write-side counterpart to the read-side bootstrap `migrations/0002_user_scoped_discovery.up.sql` solved for firm discovery. One `audit_log` row is written for the firm's creation, same table/shape the workflow engine already writes to.
- **`purchase_order.go`**/**`task_approval.go`** (`internal/workflow`) are this batch's two new minimal starter workflows, seeded only when the wizard's corresponding question is answered "yes" (see above): **Purchase Order** is `draft` (initial) -> `sent` -> `received`/`cancelled` (both terminal, only reachable from `sent`) - see the "Financial management core" section above for its `receive`-only journal template and its `total_amount`/`supplier_name` payload fields; **Task / Approval** is `open` (initial) -> `in_progress` -> `done`/`rejected` (both terminal, only reachable from `in_progress`) - see the "HR core" section below for its `assignee_person_id` payload field (a later batch's addition, `FieldTypePerson`).
- **Default role's permissions**: for each workflow `CreateDefaultFirm` actually seeds, it passes the new `owner` role's ID into that workflow's `SeedWorkflowTx` function, so `DefineWorkflowTx`'s self-action auto-grant (see the workflow engine section above) grants that role every permission the seeded workflow introduces - `CreateDefaultFirm` itself has no bespoke grant step. There is nobody else yet to grant permissions to the founder, so "everything this firm's own provisioning has introduced so far" is the deliberate default, not a restricted starter role - and it's not a superuser bypass either: see `migrations/0004_role_owner_flag.up.sql`'s `is_owner` column, which marks the role for Permission Audit Mode's future UI (Vision §3: "roles at the highest permission tier ... don't appear in these lists") but is never consulted by `permission.Has` or any other check.
- HTTP surface (not scoped under `/api/firms/{firmID}/...` - no firm exists yet, same bootstrap category as `/api/me`): `GET /api/wizard/nodes/{nodeKey}` reads a node; `POST /api/wizard/nodes/{nodeKey}/answer` submits an answer and, if it resolves to `create_default_firm`, creates the firm inline (using that path's baked-in `SeedSelection`) and returns it as `result` - see `docs/api/openapi.yaml`. The frontend's `WizardClient.tsx` collects the firm name once, up front, and carries it through every answer submitted from then on (rather than only validating it on a hardcoded `"no"` answer, which was specific to the old single-question tree) - any question could now turn out to be the tree's last one.

## Invites

Open Points item 17 (email integration) stays fully deferred - no SMTP config, no email templates, nothing that assumes a message gets delivered anywhere. This section resolves a narrower, previously-undocumented gap: there was no way at all for a second real person to get into a firm (`internal/permission.ListMembers`' own doc comment used to call this out explicitly). The mechanism is a shareable link an owner copies out of the UI and hands to someone by whatever channel they already use - nothing here sends anything.

**Self-registration investigation (read this before assuming it's off).** `deploy/keycloak/zonaryos-realm.json` previously set none of `registrationAllowed`/`registrationEmailAsUsername`/`verifyEmail`/`loginWithEmailAllowed` at all, so Keycloak's own defaults applied - `registrationAllowed` defaults to `false`, meaning self-registration was genuinely off. Investigated whether turning it on is compatible with this project's "no email infrastructure" boundary, rather than assuming either way:

- `verifyEmail` also defaults to `false`, and this realm file has no `smtpServer` block anywhere - so `registrationAllowed: true` does **not** implicitly require Keycloak to send a verification email. The realm now sets `registrationAllowed: true`, `registrationEmailAsUsername: true` (no separate username field to collide with email), and `verifyEmail: false`/`loginWithEmailAllowed: true` explicitly (not left to defaults, so the decision is visible in the file itself, not implicit). `resetPasswordAllowed` is deliberately left unset/off - Keycloak's forgot-password flow does need to send an email, which the "no email infrastructure" boundary rules out; revisit only if/when item 17 is actually resolved.
- Verified this is genuinely reachable in this deployment's actual setup, not just theoretically on by config: the `zonaryos-web` client's `redirectUris` are wildcarded (`http://localhost:3000/*`, `https://zonaryos.duckdns.org/*`), so Keycloak's registration endpoint (`{issuer}/protocol/openid-connect/registrations`, same query params as `.../auth`) redirects back through the exact same callback the login flow already uses. `deploy/nginx/zonaryos.conf`'s `/auth/` location proxies every path under Keycloak's realm generically (no sub-path allowlist), so the registration endpoint is reachable in production the same way login already is. `KC_HOSTNAME` (`docker-compose.prod.yml`) already includes the `/auth` prefix the whole realm sits behind, the same one the previously-verified interactive login round-trip (see git history) already exercises.
- **Proven end-to-end against a real, freshly-imported standalone Keycloak** (`make dev-up-standalone`, after wiping its H2 data directory so the updated realm JSON actually re-imports instead of "realm already exists, import skipped" - a real gotcha for anyone re-running this): `GET {issuer}/protocol/openid-connect/registrations?...` (same params `/api/auth/login` builds) returns Keycloak's actual registration form (200, a real `<form>` with `email`/`firstName`/`lastName`/`password` fields, no separate `username` - confirming `registrationEmailAsUsername`), and submitting it (`curl -b/-c` round-trip) redirects straight back to `redirect_uri` with a real authorization `code` - no email-verification interstitial, no error. **Conclusion: self-registration is genuinely wired in, not a fallback plan.**

**Frontend wiring for self-registration + return-path round-trip** (`web/src/app/api/auth/login/route.ts`, `.../callback/route.ts`):

- `GET /api/auth/login` now accepts two optional query params. `mode=register` sends the visitor to Keycloak's `.../registrations` endpoint instead of `.../auth` (same query params either way - PKCE/state/redirect_uri are identical). `returnTo` (a same-origin, root-relative path only - `isSafeReturnTo` rejects anything else, an open-redirect guard) is where `/api/auth/callback` should land the browser after a successful login/registration, instead of its old hardcoded `/`.
- `returnTo` is carried through the redirect round-trip via a third short-lived httpOnly cookie (`zonaryos_oauth_return_to`), set alongside the existing `zonaryos_pkce_verifier`/`zonaryos_oauth_state` cookies and read/deleted by the callback - reusing this codebase's existing "value only this login attempt needs, matched back up in the callback" mechanism rather than folding it into the `state` param itself (which already has one job: CSRF-binding the request to the callback). `isSafeReturnTo` is re-checked in the callback too (defense in depth - a cookie is still attacker-influenceable in principle, even though this app's own login route is the only writer).

**Token design and RLS** (`migrations/0007_firm_invites.up.sql`, `internal/platform/db.WithInviteTokenContext`): `firm_invites` (`firm_id`, `role_id`, `token`, `status` - pending/used/revoked, `expires_at`, `created_by_user_id`, `created_at`, `used_at`, `used_by_user_id`) is tenant-scoped like every other per-firm table (Never-Violate Rule 3), with one deliberate read-side carve-out mirroring `migrations/0002_user_scoped_discovery.up.sql`'s own reasoning for `user_firm_roles`: the accept flow has to look up a token *before* the accepter has any firm context at all (they're not a member yet - that's the entire point). `app_current_invite_token()` (a new session-setting-backed SQL function, same shape as `app_current_user_id()`) lets the RLS policy's `USING` clause also match "the row whose token equals the token this transaction was scoped to" - the token is 32 random bytes (`crypto/rand`, the direct Go-stdlib analog of `web/src/lib/pkce.ts`'s `generateCodeVerifier`, which is TypeScript and not importable from the backend), unguessable enough that possessing it is a real credential, the same trust model an unlisted share link uses. `WITH CHECK` is **not** widened the same way - every INSERT/UPDATE still requires an established `firm_id` context, so `internal/invite.Accept` sets `app.current_firm_id` itself once the invite's firm becomes known mid-transaction, the exact same manual two-step sequencing `internal/wizard.CreateDefaultFirm` uses for its own first insert. `internal/platform/db.WithInviteTokenContext` is the reusable helper for the token-scoped half (mirrors `WithUserContext`).

**`internal/invite`** (`invite.go`, `handlers.go`, `errors.go`):

- **`Generate`** (owner-gated, `IsMember` then `IsOwner`) validates `roleID` by simply reading it back inside the same firm-scoped transaction - `roles`' own RLS policy makes a role ID from a different firm structurally invisible to that query, so a cross-firm role-ID mixup is rejected the same way a genuinely nonexistent role ID is (`ErrRoleNotFound`), with no separate "does this role belong to this firm" check to get wrong. Expires `DefaultExpiry` (7 days) from creation.
- **`List`**/**`Revoke`** are owner-gated the same way (a firm's outstanding invites are membership-*shaping* information, the same tier as role create/rename/delete - not the looser plain-membership gate `ListMembers` itself uses). `Revoke` marks `status = 'revoked'`, never deletes the row - matching `internal/permission.DeleteRole`'s own soft-state precedent - and rejects revoking an already-used/revoked invite (`ErrInviteNotPending`) rather than silently no-op'ing.
- **`Lookup`** (no auth, no firm context) resolves a token to firm/role names plus its status - `ErrInviteNotFound` only for a token that never existed at all; every other non-happy-path (used, revoked, pending-but-expired) is a *successful* response whose `Status`/`Expired` fields describe why, so the frontend can show a distinct, correct message per state instead of one generic error. Expiry is derived from `expires_at` at read time, never persisted as its own status value - an expired invite's stored `status` is still `'pending'`.
- **`Accept`** (requires an authenticated caller, deliberately **not** firm membership - the one place in this codebase that must work for someone who isn't a member of the target firm yet, flagged with `ciaudit:ignore-firmid-check` since it derives `firmID` from the token rather than accepting one as a parameter) locks the invite row (`SELECT ... FOR UPDATE`) inside one transaction so the pending-check and the state change can't race apart: rejects used/revoked/expired with distinct errors, then grants `user_firm_roles` (`ON CONFLICT DO NOTHING` - a duplicate-click re-accept of the same role is a harmless no-op, not an error) and marks the invite used, all atomically. Writes an `audit_log` entry (`entity_type` `"firm_invite"`, actions `create`/`revoke`/`accept`) reusing `internal/auditlog.Write`, same as every other membership-affecting action in this codebase.
- HTTP surface: `POST`/`GET /api/firms/{firmID}/invites` (owner-only, generate/list), `POST /api/firms/{firmID}/invites/{inviteID}/revoke` (owner-only), `GET /api/invites/{token}` (public, no bearer token at all), `POST /api/invites/{token}/accept` (bearer token required, no firm-scoping). See `docs/api/openapi.yaml` for full request/response shapes.

**Frontend** (`app/[locale]/invite/[token]/page.tsx`, `components/Invite/AcceptInviteButton.tsx`, `components/AuditMode/InvitesManager.tsx`, `lib/invite.ts`): `/invite/{token}` is a public page - it never calls `requireFirmContext` and works for a visitor with zero firm memberships, unlike everything under `/settings`. It calls `lookupInvite` (`GET /api/invites/{token}`, no proxy route needed - same "server component calls a `lib/` fetch helper directly" shape `/settings/members` already uses for read-only data) and renders one of: network error, not-found, already-used, revoked, expired, or (the happy path) the invite's firm/role plus either an `AcceptInviteButton` (signed in) or Sign-in/Create-account links (`/api/auth/login?returnTo=...` and `?mode=register&returnTo=...`) built from the page's own URL. `AcceptInviteButton` posts to `/api/invite-accept/[token]` (a proxy route injecting the bearer token a client component can't read itself) and, on failure, calls `router.refresh()` instead of rendering its own error copy - the server component re-runs `lookupInvite` and shows whichever specific message now applies, so there's exactly one place deciding what each invite state's message says. `InvitesManager.tsx` (owner-gated, rendered on `/settings/members` below the existing roster - not a new top-level route) is `RoleManager.tsx`'s own create-row/list/revoke shape applied to invites: generating one shows the link once (with a copy button) via `POST /api/invites/[firmId]`, the existing table lists every invite's role/status with a revoke action (`POST /api/invites/[firmId]/[inviteId]/revoke`) for pending ones. Offered roles exclude the owner-flagged role, same as `RoleManager.tsx`'s own precedent (`GetFirmPermissionAudit`'s `is_owner` exclusion) - a scope choice for this batch, not a backend-enforced boundary (`internal/invite.Generate` itself would accept an owner-role ID if asked).

## Permission Audit Mode

Vision §3's "Yetki Denetim Modu": the UI layer that makes the permission keys already tagged on interactive elements (`AvailableAction.PermissionKey`, the stock page's `data-permission-key`) visible and editable to a firm's owner, on the actual live screens rather than a separate admin panel.

- **Who can use it**: Vision §3 scopes it to "an authorized user" without defining the term further. This codebase's working assumption - **not derived from an explicit Vision decision, flagged here rather than silently picked**: "authorized" means holding an owner-flagged role (`roles.is_owner`, `migrations/0004_role_owner_flag.up.sql`), checked via `internal/permission.IsOwner`. No separate `manage_permissions`-style permission key exists yet. If a firm later wants to delegate Permission Audit Mode to a non-owner role, that needs its own decision (and probably its own permission key) - out of scope here.
- **`internal/permission.GetFirmPermissionAudit`** is the one read call Audit Mode needs: the caller's own permission keys (across every role they hold, so their own badges are accurate even though owner roles are excluded below) plus every **non-owner** role's grants - Vision §3: "roles at the highest permission tier ... don't appear in these lists." The exclusion happens in the SQL (`WHERE NOT r.is_owner`), not just in what the frontend chooses to render - never trust the client for that.
- **`GrantPermission`/`RevokePermission`** are owner-gated (`IsMember` then `IsOwner`, same order as every firm-scoped write in this codebase) and independently re-check that the target role isn't owner-flagged (`ErrOwnerRoleImmutable`) even though the frontend never offers one as a target - the server-side check is what actually matters. Both are idempotent (`ON CONFLICT DO NOTHING` / a `DELETE` that's a no-op if nothing matched) and write one `audit_log` row each (`entity_type` `"role_permission"`).
- **Live-session propagation** (Vision §3: "active sessions for the affected role are reconnected... other admin screens are notified of the change live"): implemented as an in-process Server-Sent Events broadcaster, `internal/permission.Broadcaster` - `GET /api/firms/{firmID}/permission-events` holds one connection open per browser tab and receives a `permissions-changed` event every time `Broadcaster.Publish(firmID)` runs (called by the grant/revoke handlers after a successful commit). Open to **any firm member**, not owner-only like the audit/grant/revoke endpoints - the sessions that need to "reconnect" are the affected role's own, not just an owner watching Audit Mode.
  - **Why in-process instead of a message broker**: ZonaryOS is a single deployable binary (Never-Violate Rule 5) with no existing pub/sub infrastructure - the NATS JetStream mentioned in Vision §4 is earmarked for the Edge Agent's offline buffering, a different concern, not general-purpose pub/sub. Keycloak-backed bearer-token auth also carries no server-side session store this could hook into. A `map[firmID]map[chan struct{}]struct{}` guarded by one mutex is the least invasive mechanism that satisfies the requirement today.
  - **The tradeoff**: this stops working the moment ZonaryOS runs as more than one server process (each process would have its own, disconnected set of subscribers) - fine for now, since nothing about the current deployment model runs multiple instances, but worth revisiting explicitly if/when horizontal scaling becomes real. Noted here rather than silently designed around, since it's exactly the kind of thing that should become an Open Points entry if it starts to matter.
  - Events carry no payload beyond their name - subscribers always re-fetch full current state (`GetFirmPermissionAudit` again, or a page's own data) on wakeup rather than trying to apply a diff, so a client that missed an intermediate event because the channel coalesced two `Publish` calls into one wakeup still ends up correct.
  - **What "reconnected... immediately" does *not* require here**: the backend was never caching permissions - `permission.Has`/`IsMember`/`IsOwner` query the database fresh on every request, so a revoked permission is already enforced on the very next API call with zero propagation delay, before this SSE mechanism exists at all. What SSE actually fixes is the **UI** reflecting a change without a manual reload - Audit Mode badges updating, and (via `router.refresh()`) any server-rendered data on the page.
- **`identity.RoleInFirm`/`GET /api/me/firms/{firmID}/role`** gained an `isOwner` field so the frontend can decide whether to show the Audit Mode toggle at all, without a new endpoint - this is exactly the "once a firm has been chosen" partner endpoint `Memberships`' doc comment already pointed to for firm-scoped role detail.
- **Distinguishing "untagged" from "intentionally public"** (frontend, `web/src/components/AuditMode`): an interactive element with neither `data-permission-key` nor `data-permission-public="true"` is flagged with the Vision §3 warning badge ("this button isn't wired to any permission check - it may have been forgotten"). `data-permission-public` is the explicit opt-out for elements that are interactive but never meant to be permission-gated - sign-in/sign-out links, the wizard's pre-firm answer buttons, navigation links, and Audit Mode's own overlay controls (to avoid the mechanism flagging itself). Every existing interactive element outside the stock page's "Sell" button was retrofitted with one or the other as part of this feature - see the component for the full list.

HTTP surface (mirrors the existing `/api/firms/{firmID}/...` convention):

- `GET /api/firms/{firmID}/permission-audit` — the role-permission matrix (owner-only)
- `GET /api/firms/{firmID}/permission-catalog` — every permission key that exists for the firm (across every workflow definition), and which non-owner roles hold each - including a key nobody's been granted yet (owner-only; see "Permission Management Page" below)
- `PUT /api/firms/{firmID}/roles/{roleID}/permissions/{key}` — grant (owner-only, idempotent)
- `DELETE /api/firms/{firmID}/roles/{roleID}/permissions/{key}` — revoke (owner-only, idempotent)
- `GET /api/firms/{firmID}/permission-events` — SSE stream (any member)
- `POST /api/firms/{firmID}/roles` — create a new, non-owner role (owner-only; see "Role Management" below)
- `PATCH /api/firms/{firmID}/roles/{roleID}` — rename a role (owner-only, rejects an owner-flagged target)
- `DELETE /api/firms/{firmID}/roles/{roleID}` — delete a role (owner-only, rejects an owner-flagged target or one that still has members)
- `GET /api/firms/{firmID}/members` — the firm's roster (any member; see "Firm Members" below)

### Role Management

Item 5: `internal/wizard.CreateDefaultFirm`'s own doc comment already said the firm owner is expected to configure roles for others via Permission Audit Mode - but until this batch, there was no way to create a role at all. Every firm was permanently stuck with exactly the one `is_owner` role the wizard seeds. `internal/permission/roles.go`'s `CreateRole`/`RenameRole`/`DeleteRole` close that gap, all owner-gated the same `IsMember`-then-`IsOwner` order as everything else in this package.

- **The `is_owner` role can never be renamed or deleted through this surface.** `RenameRole`/`DeleteRole` both call the same `checkRoleIsGrantable` helper `GrantPermission`/`RevokePermission` already used to reject an owner-flagged target (`ErrOwnerRoleImmutable`) - reused, not reimplemented. This is deliberate: the `is_owner` flag is the one structural anchor the rest of the permission system depends on (Permission Audit Mode's "roles at the highest permission tier don't appear in these lists" exclusion, and every `IsOwner` check in this codebase) - there is no legitimate reason for it to ever be renamed away from being recognizable or removed. Covered by `TestRenameRole_RejectsOwnerRoleTarget`/`TestDeleteRole_RejectsOwnerRoleTarget`.
- **Deleting a role that still has members is blocked (`ErrRoleHasMembers`, 409), not cascade-unassigned.** This schema has no "reassign to a default role" concept for `user_firm_roles` - that table's `role_id` foreign key is itself `ON DELETE CASCADE`, meaning a cascading role delete would silently remove those members' firm membership *entirely*, not just their role. Silently kicking someone out of a firm as a side effect of tidying up roles is a far more surprising and harder-to-reverse outcome than a blocked delete with a clear reason, and there's no product decision (or UI) yet for "move these members to another role first" - so the safer option was chosen, the same "real 4xx, not a silent side effect" shape `internal/workflow.ErrDefinitionKeyExists` already established for its own conflict case. `role_permissions` rows for a *successfully* deleted role are still cleaned up automatically via their own `ON DELETE CASCADE` - nothing orphaned there. Covered by `TestDeleteRole_BlockedWhileMembersExist` (blocked) and `TestDeleteRole_OwnerCanDeleteEmptyNonOwnerRole` (succeeds, and cascades `role_permissions`).
- **A new role starts with zero grants**, and needs no new read-path code to show that: `GetFirmPermissionAudit`/`GetFirmPermissionCatalog`'s existing `LEFT JOIN`-based queries already list every non-owner role regardless of whether it has any `role_permissions` rows yet.
- **Frontend** (`web/src/components/AuditMode/RoleManager.tsx`, rendered on `/settings/permissions` alongside the existing permission catalog table): create/rename/delete, proxied through `web/src/app/api/permission-audit/[firmId]/roles/...` routes (same cookie-to-Bearer-token, no-authorization-decision-here pattern as every other proxy route). Deliberately does **not** render each role's own grants - the permission catalog table it sits above already shows, for every permission key, which role keys hold it, so a newly created role simply not appearing in any row's chips *is* "starts with zero grants," reusing that existing render path per item 2's explicit instruction rather than duplicating it.

### Firm Members

Item 3: a plain, view-only roster - who's in the firm, and which role they hold (`internal/permission.ListMembers`, a `user_firm_roles` join against `users`/`roles`, no new schema concept). Membership-gated only (`IsMember`), not owner-only like Permission Audit Mode's own reads - "who's on my team and what's their role" isn't treated as owner-only sensitive information in this codebase, the same visibility level as the generic workflow instance list. A user holding more than one role in the same firm (`user_firm_roles`' `UNIQUE` constraint is `(user_id, firm_id, role_id)`, not `(user_id, firm_id)`) appears once per `(user, role)` pairing, not collapsed into a single row - verified by manually granting a second role to the same user and confirming `GET .../members` returns both rows during this batch's live verification.

With no invite/email flow yet (Open Points item 17, still deferred), `web/src/app/[locale]/settings/members/page.tsx` will only ever show the one row for whoever ran the firm-creation wizard today - expected, forward-compatible groundwork, not a claim that onboarding a second user already works. The page renders an explicit note under a single-row roster ("you're the only member so far") rather than leaving that state to look like a broken or half-loaded page.

### Permission Management Page

Item 3: Audit Mode's live badge overlay is per-page and transient - it only ever shows the one permission key attached to whatever element you click, on whatever screen that element happens to render on. `/settings/permissions` (`web/src/app/[locale]/settings/permissions/page.tsx`) is the static, browsable counterpart: every permission key that exists for the firm, across every workflow definition, and which roles hold each, on one page - not a second editing surface (granting/revoking still happens through Audit Mode's own popup, which already covers that).

- **`internal/permission.GetFirmPermissionCatalog`** is the backend read call, and it's built *on top of* `GetFirmPermissionAudit` (Audit Mode's own grant/revoke popup's data source) rather than a second, parallel query/authorization path - same owner-only gate, same is_owner-role exclusion, obtained by literally calling `GetFirmPermissionAudit` internally. What it adds: a firm-scoped union of every `permissions.key` referenced by the firm's own `workflow_definitions.create_permission_key`/`workflow_transitions.permission_key`, plus every key any non-owner role already holds (covers a key with no workflow-engine origin at all, e.g. `audit.log.read`) - so a key that's been defined on a transition but never granted to anyone still shows up, with zero role holders, which `GetFirmPermissionAudit`'s role-keyed shape has no way to represent (a key with zero holders has no role row to attach to). Carries a `ciaudit:ignore-firmid-check` comment (see `cmd/ciaudit`'s own doc comment on why this suppression category exists) since the firmID-membership check happens inside the `GetFirmPermissionAudit` call it delegates to, not redundantly in its own body.
- The frontend (`fetchFirmPermissionCatalog`, `web/src/lib/permissionAudit.ts`) reads `GET /api/firms/{firmID}/permission-catalog` and renders one row per key: the key itself, its `permissions.description`, and the non-owner roles currently holding it (or an explicit "no roles yet" for one that isn't). Owner-gated the same way `audit-log/page.tsx` is (`role.isOwner`, not a permission-catalog key - see this section's "Who can use it" note above for why that's the working assumption throughout Permission Audit Mode).

## Audit Trail Infrastructure

`internal/auditlog` is Vision §3's Audit Trail Infrastructure: every operation should be traceable "at the most detailed level" - both data changes and view/read access - readable by the firm owner (and, later, an "Auditor Role") and nobody else.

- **Data-change coverage**: the write-side pattern already existed before this package (`internal/workflow.CreateInstance`/`ExecuteTransition`, `internal/wizard.CreateDefaultFirm`, `internal/permission.GrantPermission`/`RevokePermission` each write one explicit `audit_log` row) and is left as-is - this codebase's modular-monolith style favors an explicit "log this write" call at each mutation point over a generic diffing framework (see `CLAUDE.md`). `auditlog.Write` exists so *new* write call sites share one `INSERT` instead of duplicating it; the existing four call sites above predate it and were not retrofitted, since `internal/permission` can't import `internal/auditlog` without an import cycle (`auditlog` itself depends on `internal/permission` for read-gating, see below) and touching the other three wasn't necessary to close any actual gap - firm creation, workflow transitions, and permission grant/revoke already covered every data-changing operation this slice has.
- **View/read logging** (`auditlog.LogView`): Vision §3 explicitly calls for logging reads too, not just writes - and explicitly flags this as the part with unresolved legal exposure (see docs/OPEN_POINTS.md item 33: whether retaining detailed view/read records, particularly employee access records, creates a KVKK issue is an open question requiring legal counsel). Rather than wiring every read endpoint in the system into this mechanism, only one representative path does: `internal/workflow.ListInstances` (the stock list's data source, PR #8) writes one `action: "view"` entry per call. Every other read path (`CurrentState`, `LookupDefinitionByKey`, Permission Audit Mode's own reads, the audit log read itself) is deliberately left unwired - broader rollout is future work pending that legal-review decision, not an oversight.
- **`auditlog.ReadPermission`** (`audit.log.read`) gates `GET /api/firms/{firmID}/audit-log` through the ordinary `permission.IsMember` + `Has` check (docs/DEVELOPMENT.md's own Authorization checklist above), not a hardcoded `IsOwner` check like Permission Audit Mode uses. The Auditor Role Vision §3 describes isn't designed or built in this PR (no external-auditor-invitation flow exists) - gating on a permission key instead of ownership means a firm can extend audit log access to any future Auditor Role later, purely by granting it this key via Permission Audit Mode, with no code change here. `internal/wizard.CreateDefaultFirm` grants it to every new firm's own owner role at creation time (`auditlog.RegisterReadPermissionTx`, the same self-action-auto-grant shape `workflow.DefineWorkflowTx` already established for workflow-introduced permissions).
- **Retention**: docs/OPEN_POINTS.md item 33 leaves the actual retention period - and even whether automatic deletion is appropriate at all, given the KVKK question above - unresolved; Vision §3's own "at least 10 years" figure is explicitly marked not finalized. Nothing in this codebase hardcodes a retention duration. `auditlog.PurgeOlderThan` is a plain, firm-by-firm (RLS-respecting) deletion function that takes an explicit cutoff; the only caller is `cmd/auditpurge` (`make audit-purge`), a manually-invoked maintenance command that refuses to run at all unless an operator has explicitly set `ZONARYOS_AUDIT_RETENTION_DAYS` to a positive integer - there is no default to fall back to, and `cmd/server` never invokes it automatically.
- **Pagination and filtering** (Open Points item 36's sibling task): `List` now takes a `ListOptions{Limit, Offset, From, To, DefinitionID}` - the zero value returns every entry unfiltered/unpaged, exactly `List`'s original behavior, so every pre-existing caller keeps working unchanged. `Limit`/`Offset` mirror `internal/workflow.ListInstances`'s own `ListInstancesOptions` shape exactly (one `COUNT(*) OVER()` alongside the paged rows reported as `ListResult.Total`, capped server-side at 200 via the HTTP handler). `From`/`To` (`*time.Time`, nil meaning "no bound") filter on `occurred_at`, inclusive on both ends. `DefinitionID` (`*uuid.UUID`) filters to entries that resolve back to that workflow definition: `audit_log` has no `workflow_definition_id` column of its own, so this is a `LEFT JOIN workflow_instances ON al.entity_type = 'workflow_instance' AND al.entity_id = wi.id`, matching on `wi.workflow_definition_id` - the honest, practical scope given `Entry`'s real fields, not a fabricated filter. An entry unrelated to any workflow instance (a firm rename, a permission grant, ...) never matches a `DefinitionID` filter, which is correct: it genuinely isn't about any workflow definition.

HTTP surface:

- `GET /api/firms/{firmID}/audit-log` — the firm's audit trail, most recent first (gated by `audit.log.read`); optional `?limit=`/`?offset=` paging (`X-Total-Count` response header carries the filtered-but-unpaged total, same convention as the workflow-instances list endpoint), `?from=`/`?to=` (RFC3339) date-range filtering, `?definitionId=` workflow-definition filtering. Every query param is optional; omitting all of them returns every entry, unpaged, unchanged from this endpoint's original behavior.

## License Verification

`internal/license` is the technical-friction layer of Open Points item 32 ("License Verification Mechanism") - Vision §5's "3-Layer Defense," layer 2 only (layer 1, the real deterrent, is the license agreement - item 20). **Disabled by default, and this is a structural guarantee, not an incidental one**: `internal/license.Verifier.Allow` (the one gate every call site uses) returns `nil` as its literal first statement whenever `ZONARYOS_LICENSE_ENFORCEMENT` is not exactly `"true"`. Nobody needs to read this section or set any of the env vars below to keep working exactly as before this batch existed - this is entirely opt-in.

- **Token format and signature scheme**: Ed25519 (`crypto/ed25519`, no third-party crypto dependency), NOT the Developer's original MD5-based raw idea (`docs/OPEN_POINTS.md` item 32) - MD5 is broken for integrity/authenticity purposes and can't prove authorized issuance the way a signature can. A token is `<base64url(payload JSON)>.<base64url(Ed25519 signature over the payload JSON bytes)>` - see `internal/license/license.go`'s package doc comment for the exact wire format. Payload: an opaque firm/installation identifier, an expiry timestamp, and a list of active module keys.
- **Server-side secret, client-only-implements-a-protocol** (item 32's open question 4, now answered): this codebase holds only the Ed25519 *public* key (`ZONARYOS_LICENSE_PUBLIC_KEY`) - it can verify a token's signature but can never mint one, since it never holds the matching private key.
- **Module gating**: a small, honest, deliberately provisional stand-in for item 30's still fully-open real module/pricing catalog - `internal/license.ModuleWorkflowEngine`/`ModuleAuditTrail`/`ModulePlatformAdmin`. Only `ModulePlatformAdmin` is actually wired into a real gate today: `internal/platformadmin.ListFirms` (`GET /api/platform-admin/firms`) calls `license.Verifier.Allow(license.ModulePlatformAdmin)` right after its existing allowlist check, before any database access - chosen as the lowest-blast-radius illustrative fit (see that package's own doc comment for the reasoning). When enforcement is enabled and denied, that endpoint now returns `503 Service Unavailable` with the license error's own actionable message (not `401`/`403`/`404` - the caller's identity/authorization was never in question, only the installation's own license state).
- **Grace period**: `ZONARYOS_LICENSE_GRACE_PERIOD` (a Go duration string, e.g. `72h`), how long past a token's expiry `Allow` keeps allowing access before failing closed. Defaults to `internal/license.DefaultGracePeriod` (72h) - a **PROVISIONAL DEFAULT, NOT A DECIDED SLA**, same honesty `deploy/backup/backup-postgres.sh`'s own backup-retention default carries for its own still-open Open Points item.
- **Periodic re-check**: when enforcement is enabled, `cmd/server/main.go` starts one background goroutine (a plain `time.Ticker`, no daemon framework - there's no existing precedent for one in this codebase) that calls `Verifier.Check()` every `license.RecheckInterval` (15 minutes) so a long-running server process catches its own token's expiry crossing over time, not just at startup. No goroutine at all is started when enforcement is disabled.

## Central-server discovery and usage telemetry

Open Points item 40 (`docs/OPEN_POINTS.md`). Two packages, built together because the second depends on the first: `internal/discovery` (shared "where is the central server right now" client, used today only by `internal/telemetry` - see below for why `internal/license` doesn't need it yet) and `internal/telemetry` (aggregate, non-content usage telemetry - request/feature counts and source IPs, never content). Both hold to the exact same "structural, not incidental" default-disabled-guarantee rigor `internal/license.Verifier.Allow` established (see the "License Verification" section above) - `internal/telemetry` doubly so, since it collects source IP addresses, real privacy-sensitive data (see the KVKK cross-reference this batch adds to `docs/OPEN_POINTS.md` items 33 and 40).

### Discovery (`internal/discovery`)

- **The well-known endpoint**: every installation serves `GET /.well-known/zonaryos-central`, answering with `{"centralUrl": "<this installation's own ZONARYOS_PUBLIC_URL>"}` - self-referential today, since Open Points item 34's real separate central server doesn't exist yet. `ZONARYOS_PUBLIC_URL` reuses `docker-compose.prod.yml`'s existing `KC_HOSTNAME` convention ("what is my own public URL") rather than inventing a second one - e.g. `https://zonaryos.duckdns.org` in production, unset (empty) in plain local dev. This endpoint is unauthenticated and has no default-off gate (unlike telemetry below) - see `internal/discovery.RegisterRoutes`'s own doc comment for why.
- **The discovery client**: `internal/discovery.Client`, built once in `cmd/server/main.go` from `ZONARYOS_DISCOVERY_START_URL` (defaults to `ZONARYOS_PUBLIC_URL` when unset). `Resolve(ctx)` returns the current best-known central address: a cached value fresh within `internal/discovery.DefaultTTL` (1 hour, a **PROVISIONAL DEFAULT, NOT A DECIDED value** - same honesty as `license.DefaultGracePeriod`) is returned with no network call; once stale, it re-fetches the well-known document from wherever it *last* successfully resolved to (not back to the original start URL) - this is what makes a real future migration a chain (A points to B, B later points to C, and A's client - still holding B as its cache - asks B and learns C, without ever needing to know about C directly).
- **Fallback behavior, the core resilience property**: if the fetch fails, `Resolve` falls back to the **last-known-good cached address** - never a hardcoded default. On a genuine first-ever resolution (fresh process, nothing cached yet, and the very first fetch also fails), it falls back to `ZONARYOS_DISCOVERY_START_URL` itself, treated as the zeroth-generation "last known good" (the only address this installation was ever told to trust) - see `Client`'s doc comment for the full reasoning.
- **`internal/license` does not use this yet, and that's an honest finding, not an oversight**: `internal/license` is fully local/static today (`ZONARYOS_LICENSE_TOKEN` is a config value, never fetched over the network - see that package's own doc comments) - there is nothing for it to resolve "where is the central server" for. `internal/discovery.Client` is designed to be ready as that shared resolver once license verification does grow a real network call (item 34), so that `internal/license` and `internal/telemetry` end up sharing one HTTP-fetch-with-cache implementation, not two - but forcing a dependency onto `internal/license` today would be artificial.

### Usage telemetry (`internal/telemetry` + `web/src/lib/telemetry.ts`)

**Absolute rule**: aggregate counts and identifiers only, never content. Page/feature counts, not what was on the page. Request counts, not request bodies. Source IPs, not payloads.

- **What's collected server-side (Go)**: per-endpoint request counts (`"METHOD /registered/{pattern}"`, e.g. `"GET /api/firms/{firmID}"` - never the resolved path-parameter value) and source IP counts, via `telemetry.Middleware` wrapping the whole `*http.ServeMux` in `cmd/server/main.go`.
- **What's collected client-side (web)**: page/route view counts and named feature-usage-event counts (e.g. `workflow_instance_created`, `workflow_transition_executed:<actionKey>`) - counts of actions the frontend already observed succeeding (its own `POST /api/workflow/instances` and `.../transitions/{actionKey}` route handlers, after `createInstance`/`executeTransition` return `ok: true`), not new instrumentation reading business data. Browser-side counts (`web/src/lib/telemetry.ts`, mounted via `components/Telemetry/TelemetryClient.tsx` near the root layout) batch in memory and flush every 5 minutes (`FLUSH_INTERVAL_MS`, a **PROVISIONAL DEFAULT**) or on `pagehide`/tab-hide via `navigator.sendBeacon` (falling back to `fetch(..., {keepalive: true})`), never per-click.
- **Flow**: browser batches -> `POST /api/telemetry` (Next.js route, forwards to the Go backend) -> Go backend's `POST /telemetry/client-report` merges it into `internal/telemetry.Reporter`'s own counters, alongside the server-side request/IP counts -> every `telemetry.DefaultFlushInterval` (5 minutes, also provisional), the Reporter POSTs a batched `Report` to `{internal/discovery.Client.Resolve()}/telemetry/report`. Today that resolves to this same installation (self-referential, per the discovery section above), so `internal/telemetry.RegisterRoutes`'s `/telemetry/report` handler is what actually receives it - logged (a one-line count summary, never persisted to Postgres - there is no retention/access-control story for this data yet) rather than stored anywhere durable.
- **Resilience**: a flush failure (central unreachable, timeout, non-200) is logged and dropped at `Reporter.flushOnce` - the literal bottom of that goroutine's call stack, nothing above it for an error to propagate into - never retried inline, never surfaced as a user-facing error, never blocks a request. Same guarantee client-side: `lib/telemetry.ts`'s `flush()` swallows every failure.
- **Default-disabled guarantee, structural not incidental**: gated on `ZONARYOS_TELEMETRY_ENABLED` (Go backend, and the frontend's own server-only same-named var used by its API routes) plus `NEXT_PUBLIC_ZONARYOS_TELEMETRY_ENABLED` (browser-bundle-visible, build-time-inlined). `telemetry.NewReporter(false, ...)` returns a literal `nil`, not a disabled-but-allocated struct - every `Reporter` method is written to check for a nil receiver as its first statement and do nothing else, the identical shape `license.Verifier.Allow`'s own doc comment describes. `telemetry.Middleware(nil, mux)` hands back the wrapped handler completely unwrapped (no closure allocated at all). `telemetry.RegisterRoutes(mux, nil)` registers nothing - the `/telemetry/*` paths don't exist, they don't merely no-op. The periodic flush goroutine (`Reporter.Start`) is only ever launched from `cmd/server/main.go` inside an `if cfg.TelemetryEnabled` branch, matching `license.RecheckInterval`'s own goroutine-gating precedent. Client-side, `lib/telemetry.ts`'s `init()`/`recordPageView`/`recordFeatureEvent` all independently check `NEXT_PUBLIC_ZONARYOS_TELEMETRY_ENABLED` as their first statement - no timer, no event listener, no counter touched when it isn't exactly `"true"`.
- **Default value chosen: OFF.** This collects source IP addresses, real privacy-sensitive data intersecting Open Points item 33's still-fully-open KVKK question - an operator must explicitly opt in, never discover after the fact that telemetry was silently running.
- **No UI for viewing collected telemetry** (out of scope - a future admin-panel feature) and **no real separate central-server deployment** (item 34 stays open; today's "central" is this same installation, self-reporting to itself).

## Platform Admin

`internal/platformadmin` is a narrow, read-only view for ZonaryOS-the-company staff (the platform operator) - distinct from everything else in this API, which is scoped to one firm the caller belongs to. It answers a different question ("is this caller ZonaryOS staff?") than `internal/permission`/`internal/firm` ("is this caller a member/permission-holder/owner *within one firm*?"), which is why it's kept as its own package rather than folded into either.

- **Auth model**: a hardcoded allowlist of emails (`internal/platformadmin.Allowlist`), checked against the caller's already-verified Keycloak identity (`internal/identity.Identity.Email` - the same struct every handler reads from context after `internal/identity.Middleware` runs), not a new Keycloak realm/client or a parallel identity system. Populated from `ZONARYOS_PLATFORM_ADMIN_EMAILS` (comma-separated, case/whitespace-insensitive - see `internal/platform/config`), following this codebase's existing env-var config convention. Empty by default: nobody is a platform admin until this is explicitly set. A dedicated Keycloak client would buy self-service admin signup/delegation/per-admin scoping - none of which this batch needs; that's the concrete trigger to revisit this decision, not a default reached for casually.
- **What it exposes**: for every firm, `name`/`created_at` (read directly from the `firms` table, which carries no RLS policy - see `migrations/0001_core_schema.up.sql`'s comment on it) plus a workflow-definition count and a member count. Nothing else - no tenant business data (no stock items, no CRM leads, no audit log contents), no user roster (member count only, not who).
- **How the counts are obtained without any new database privilege**: this codebase's Postgres app role deliberately holds no `BYPASSRLS` (see `internal/platform/db.WithFirmContext`'s doc comment) and this package doesn't add one. Instead, `ListFirms` loops over every firm ID from the un-scoped `firms` read and opens one legitimate, firm-scoped transaction per firm via `zdb.WithFirmContext` - the exact mechanism `internal/wizard.CreateDefaultFirm` and every other tenant-scoped read in this codebase already uses - then runs `COUNT(*)` against `workflow_definitions` and `user_firm_roles` inside that RLS-scoped context. This is N legitimate, RLS-respecting per-firm reads, not a cross-firm bypass query; see `internal/platformadmin/platformadmin.go`'s doc comments (including its `ciaudit:ignore-firmid-check` suppression - the check is skipped for this one internal per-firm loop function precisely *because* the caller isn't a firm member at all, and Allowlist, not membership, is what already authorized the read one level up in `ListFirms`).
- **Accountability**: every access writes one `audit_log` row (`action: "platform_admin_metadata_view"`) into *each firm's own* audit trail, attributed to the platform admin's resolved user ID - reusing `internal/auditlog.Write` rather than a parallel logging path. `audit_log.firm_id` is `NOT NULL` and RLS-scoped to one firm (`migrations/0003_workflow_engine.up.sql`), so there's no clean way to represent one firm-less "platform-level" event in it; logging per-firm-visited instead is a deliberate, and reasonably clean, resolution of that ambiguity - the read genuinely happened while scoped to that one firm, so its own audit_log is where accountability for it belongs. A firm's own owner can see this access the same way they see any other `audit_log` entry (`GET /api/firms/{firmID}/audit-log`).
- **Ordering**: the allowlist check runs first, before `identity.ResolveOrCreateUser` or any query - a non-allowlisted caller never causes a query to run at all (see `internal/platformadmin/allowlist_test.go`'s `TestListFirms_RejectsNonAllowlistedBeforeAnyDatabaseAccess`, which proves this with a `nil` pool as a poison pill rather than just asserting the happy path is narrow).
- **Frontend gate**: `web/src/app/[locale]/platform-admin/page.tsx` is reachable only at that distinct path, outside any firm namespace, with no in-app link to it. Unlike `settings/permissions`/`audit-log` (which render an inline "not authorized" message for a real but unauthorized firm member), this route calls `next/navigation`'s `notFound()` for anyone off the allowlist - the real 404 page, as if the route didn't exist. That's a deliberate, higher-sensitivity choice for this one route given its own task brief's explicit ask, not a pattern the other owner-gated pages need to adopt.
- **License gate**: this endpoint is also the one place `internal/license`'s module-gating mechanism (see "License Verification" above) is actually wired in today - `ListFirms` calls `license.Verifier.Allow(license.ModulePlatformAdmin)` right after the allowlist check above, before any database access. With `ZONARYOS_LICENSE_ENFORCEMENT` unset (the default), this is a complete no-op - see the "License Verification" section for the structural guarantee behind that. With enforcement enabled and denied, the endpoint returns `503`, not `401`/`403`/`404`.

HTTP surface:

- `GET /api/platform-admin/firms` — firm metadata across every firm (allowlist-gated; 404, not 403, for a non-allowlisted caller; also license-gated, see above - 503 with an actionable message if enforcement is enabled and the license is invalid/expired/missing the `platform_admin` module)

### Why `make test` passes `-p 1`

Several packages' integration tests (`internal/platform/db`, `internal/identity`, `internal/workflow`, ...) share the same real Postgres database and each `TRUNCATE`s the tables it needs a clean slate for at the start of every test. `go test ./...` runs different packages' test binaries concurrently by default - fine for packages that don't share state, but two packages truncating the same tables (`firms`, `users`, `roles`, ...) at the same moment can wipe out data a sibling package's test just relied on, causing spurious failures that have nothing to do with the code under test. `go test -p 1 ./...` (what `make test` runs) forces one package at a time, which is what actually matters here - not test speed.

If you ever see a failure in one integration test package only when running the full suite, and it passes cleanly in isolation (`go test ./internal/xyz/... -v`), this is almost certainly why - not a real regression.

## Continuous Integration

- **Unit Tests** (`unit-tests-backend`, `unit-tests-frontend`): `go vet ./... && go test ./...` with no database env vars set, so every `*_integration_test.go` file self-skips via the same `t.Skip(...)` convention already documented throughout this file - not a new detection mechanism, the existing one just runs unattended now. `cd web && npm run lint && npm test` for the frontend side.
- **Integration Tests** (`integration-tests`): a real `postgres:16` GitHub Actions service container, configured identically to `docker-compose.yml`'s `postgres` service (same image, same `POSTGRES_USER`/`PASSWORD`/`DB`), so the exact `ZONARYOS_TEST_ADMIN_DATABASE_URL`/`ZONARYOS_TEST_APP_DATABASE_URL` convention this file already documents for local dev applies unchanged - `go run ./cmd/migrate` then `go test -p 1 ./...`. This is what now actually runs the RLS/tenant-isolation tests (`internal/platform/db`, and every package's own `*_integration_test.go`) on every PR - previously they only ran when a human remembered to `make dev-up` and set the env vars, the gap that let Open Points item 37 ship once before a later manual audit caught it. `internal/identity/keycloak_integration_test.go` is deliberately left out of this job's scope (no live Keycloak service container here) - it self-skips since its `ZONARYOS_TEST_KEYCLOAK_*` env vars aren't set, same as any other CI environment without a live Keycloak; still a manual (`make dev-up`/`make dev-up-standalone`) verification step for changes that touch `internal/identity` - see "Claude Code Remote sessions on this project" above for why this is achievable in a Remote session too, not just on a laptop.
- **RLS / Permission Drift Audit** (`rls-permission-audit`, `cmd/ciaudit`): a codified version of the manual trace that closed Open Points item 37. Two checks: (1) every table with a `firm_id` column across `migrations/*.up.sql` must have a matching `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` somewhere in the migrations directory (Never-Violate Rule 3); (2) every Go function/method under `internal/` with a parameter literally named `firmID` must call `permission.IsMember`/`Has`/`IsOwner` somewhere in its body (including nested closures, e.g. the `WithFirmContext` callback pattern every handler uses) - or carry a `ciaudit:ignore-firmid-check: <reason>` line in its doc comment, for the legitimate exceptions (a low-level primitive like `WithFirmContext` itself, an internal helper only reachable after its caller already checked, a provisioning-only function never reachable with a caller-supplied `firmID`). This is a static, grep/AST-level heuristic, not full data-flow analysis - it is exactly the "grep for firmID-taking functions, trace to permission.IsMember" methodology the item 37 fix already used, now run automatically instead of by hand.
- **i18n Hardcoded-String Check** (`i18n-check`, `web/scripts/check-i18n-strings.mjs`): walks every `.ts`/`.tsx` file under `web/src` with the TypeScript compiler API's own AST (not a fresh regex heuristic - `typescript` is already a devDependency), flagging any JSX text node containing letters (an expression container like `{t("key")}` is a different AST node entirely, so it's invisible to this walk - only literal text rendered directly is caught) and any string-literal `placeholder`/`aria-label`/`title`/`alt` attribute containing letters. A line can opt out with a trailing `// i18n-ignore` comment, for genuinely non-UI text (see `StockList.tsx`'s own note on why workflow state/action names rendered as-is are out of the i18n layer's scope). Plain ESM (not `.cjs`) - this repo's ESLint config flags `require()`-style imports repo-wide, this script included.
- **Permission-Tag Coverage Check** (`permission-tag-check`, `web/scripts/check-permission-tags.mjs`, Never-Violate Rule 7): the static, CI-enforced counterpart to Permission Audit Mode's live-DOM overlay (`components/AuditMode/useAuditBadges.ts`'s `scanInteractiveElements`, which only catches an untagged element when a developer actually opens Audit Mode and looks). Same AST infrastructure and file-walking as the i18n check above (TypeScript compiler API, not regex). Flags any `<button>`, any element with a literal `onClick` attribute, any `<form>` with a literal `onSubmit` attribute, and any `<a>`/`Link` with a literal `href` attribute - mirroring `useAuditBadges.ts`'s own `"button, a[href]"` selector as closely as static analysis allows, plus `<form>` (the runtime overlay never scans forms at all, so a form submitted via Enter-key rather than a click on its tagged submit button was a real, previously-unaudited gap this check closes) - that does not carry a literal `data-permission-key="<catalog-key>"` or `data-permission-public="true"` attribute. This repo's own established convention (not invented by this check) already tags *every* qualifying element this way, including plain navigation links and `is_owner`-gated elements (`data-permission-public`, since there's no permission-catalog key for a structural ownership check) - see e.g. `Nav/NavShell.tsx`, `Workflow/DefinitionBuilder.tsx`. A line can opt out with a trailing `// permission-audit-ignore: <reason>` comment - a real explanatory reason is required after the colon, mirroring `cmd/ciaudit`'s own `ciaudit:ignore-firmid-check: <reason>` convention rather than a bare suppression tag. Limitation (documented in the script's own header comment): only a literal string attribute on the element itself is checkable - a marker reached via a spread prop, applied conditionally, or forwarded through a wrapping component is out of scope without full type-flow analysis, same category of limitation as the i18n check's own `{t(...)}` key content being unverified. Built this batch after finding, beyond the two gaps (`AuditLogTable.tsx`, `AcceptInviteButton.tsx`) a prior manual architecture audit had already fixed, 21 further untagged elements across `InvitesManager.tsx`, `RoleManager.tsx`, `WorkflowInstanceList.tsx`, `CreateInstanceForm.tsx`, `DefinitionBuilder.tsx`, `GlobalSearchBox.tsx`, `AuditLogTable.tsx`'s filter form, and `FirmMetadataEditor.tsx`'s form - all fixed in the same batch that added this check (see the PR that introduced `check-permission-tags.mjs` for the full list).
- **Doc Sync Check** (`doc-sync-check`, `scripts/check_doc_sync.py`, PR-only): if the diff touches `internal/`, `cmd/`, or `web/src/`, `docs/DEVELOPMENT.md` must be part of the same diff - this file's own per-module section convention (one `## <Module>` section per feature, established across PRs #3-#10) only stays accurate if every PR that changes a module also updates its section.
- **License Header Check** (`license-header-check`, `scripts/license_headers.py`): every tracked `.go` file under `cmd`/`internal` and every `.ts`/`.tsx` file under `web/src` must start with the header in `scripts/license-header.txt` (as a `//` comment block) - see `LICENSE` (a draft, pending legal review - `docs/OPEN_POINTS.md` item 20). For a Go file, the header is its own separate comment block at the very top, blank-line-separated from whatever follows, specifically so it never attaches as that file's package doc comment (Go only treats the comment block immediately touching the `package` clause, with no blank line, as the doc comment). For a `.tsx` file opening with a `"use client"`/`"use server"` directive, the header goes immediately after it instead of before, since that directive must stay the file's literal first line. Run `python3 scripts/license_headers.py --fix` to add a missing header mechanically.
- **API Contract Diff** (`api-contract-diff`, `scripts/check_api_contract.py`, PR-only, Never-Violate Rule 6): diffs `docs/api/openapi.yaml` against the same file's content on the PR's base branch (`git show origin/<base>:docs/api/openapi.yaml` - the base branch's own history is the "previous version" baseline, no separate versioned-snapshot file needed) and fails if any documented path or HTTP method present in the base version is missing from the head version. This is a path/method-level diff only, not a full schema diff - it will not catch a removed required field, for example - a known limitation of this first version, not a silent gap left undocumented.
- **Migration Safety Check** (`migration-safety-check`, `scripts/check_migration_safety.py`, PR-only): Vision §4's active-passive multi-region architecture means a rolling deploy window can have old and new application code running against the same schema at once - a migration that isn't safely forward/backward compatible during that window is exactly the failure mode this catches. Flags, in any `migrations/*.up.sql` file *added* in the PR diff: `DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, any `ALTER COLUMN ... TYPE` (can't statically tell narrowing from widening, so any type change is flagged for manual review), and non-additive `RENAME COLUMN`/`RENAME TO`. Separately, any *existing* migration file *modified* (not added) in the diff is always flagged - migrations must never be edited after merging (a rolling deploy may have already applied the old version elsewhere). A migration can acknowledge an intentional destructive change with a `-- migration-safety:acknowledge: <reason>` comment anywhere in the file - a documented exception, still printed, not silently dropped. `.down.sql` files are never scanned: they're rollback-only by golang-migrate's own convention and legitimately contain the inverse destructive statement (see `migrations/0004_role_owner_flag.down.sql`'s `DROP COLUMN`).
- **Dependency Vulnerability Scan** (`dependency-scan-backend`/`dependency-scan-frontend`): `govulncheck` (`scripts/check_govulncheck.py`) for Go, restricted to its default "source" scan mode - only vulnerabilities actually reachable from this module's own call graph, not merely-imported-but-unused ones - failing on any finding not listed in `scripts/govulncheck-allowlist.json`. `npm audit` (`web/scripts/check-npm-audit.mjs`) for the frontend, failing on any high/critical finding not listed in `web/audit-allowlist.json`; moderate/low findings are reported but don't fail the build. Both allowlists require a `reason` and a `reviewBy` date per entry - a documented exception, not a silent ignore - and the frontend one currently has 4 real entries (postcss/sharp/brace-expansion advisories pulled in transitively by `next`/`eslint`, where npm's own proposed fix is a multi-major-version downgrade, not a safe one - see the file for the full reasoning). Both scripts fail loudly (distinct exit code) rather than silently reporting "clean" if the underlying tool itself couldn't run (e.g. couldn't reach its vulnerability database).
- **SAST Security Scan** (`sast-scan`): [gosec](https://github.com/securego/gosec) (`scripts/check_gosec.py`) for Go - purely local static analysis, no external service/login/API token - failing on any finding; a genuine false positive is suppressed with gosec's own native `// #nosec <RULE> -- <reason>` comment (two exist today, both documented inline) rather than a second, parallel allowlist file. [gitleaks](https://github.com/zricethezav/gitleaks) (`scripts/check_gitleaks.sh`, `.gitleaks.toml`) for secret scanning across git history, with a documented allowlist for one known false positive (`*_integration_test.go`'s `seedUser` helpers building a fake `keycloakSubject+"@example.com"` identifier, which the `generic-api-key` rule's entropy heuristic misreads as a key).
- **E2E Smoke Test** (`e2e-smoke-test`, `scripts/e2e_smoke_test.sh`): brings up a real stack - Postgres + Keycloak via `make dev-up-standalone` (the exact same standalone bring-up every prior PR's manual E2E verification already used, not a new sequence invented for CI), the real backend (`go run ./cmd/server`), and the real frontend (`npm run build && npm run start`) - then exercises login (a real Keycloak-issued bearer token via Direct Access Grant, verified by the real `internal/identity.Verifier`; also confirms the frontend's own `/api/auth/login` redirects to that same real Keycloak issuer) and the core transaction: wizard → firm creation → add stock → sell, asserting on real HTTP responses at every step, plus a bonus check that the audit trail (`GET .../audit-log`) recorded the transaction. A later batch extended it to also walk the wizard's second default-seeded workflow, Customer Pipeline, through create → qualify → convert, then confirm the dashboard's counts-by-state overview (`GET .../workflow-instance-counts`, plus the real `/en` dashboard page) reflects both workflows correctly, exercise quick-create from the dashboard, and confirm global search (`/en/search?q=...`) finds the converted lead grouped under Customer Pipeline. **Disclosed scope boundary**: this does not drive a headless browser through Keycloak's interactive login form (that needs Playwright + a browser download in CI, a further infra addition) - "login" here means obtaining a real token from the real Keycloak server directly, not simulating a user clicking through the browser-based PKCE redirect flow. This test found and helped fix a real bug during development (see `internal/workflow.CreateInstance`/`ExecuteTransition`'s nil-payload guard, and `TestExecuteTransition_NilPayloadDoesNotCorruptStoredPayload`): a nil payload map marshaled to JSON `null`, and Postgres's `jsonb ||` operator silently corrupted the stored payload into an array instead of leaving it untouched.

### Running the CI checks locally

```
go build ./...
go vet ./... && go test ./...
go run ./cmd/ciaudit
python3 scripts/license_headers.py --check      # or --fix to add missing headers
python3 scripts/check_gosec.py
python3 scripts/check_govulncheck.py
cd web && npm ci && npm run build && npm run lint && npm test && npm run check:i18n && npm run check:permission-tags && npm run check:audit
```

The Postgres-backed integration test job, Doc Sync Check, API Contract Diff, and Migration Safety Check need either a real Postgres (see "Running the RLS integration tests" above) or a base ref to diff against (`python3 scripts/check_doc_sync.py origin/main` / `python3 scripts/check_api_contract.py origin/main` / `python3 scripts/check_migration_safety.py origin/main`) - all fine to run locally against a local clone with `main` fetched. `scripts/check_gitleaks.sh` needs `gitleaks` installed (`go install github.com/zricethezav/gitleaks/v8@latest`) and on `PATH`. `scripts/e2e_smoke_test.sh` needs the full standalone stack up (`make dev-up-standalone && make migrate`, the backend running, and the frontend built and started) - see the job definition in `.github/workflows/ci.yml` for the exact sequence.

### Context-Loss Tactics: PR review-comment catch-up

(No prior "Context-Loss Tactics" section existed in this repo before this note - this is the first one, added here per the Notion Development Process page §8. If a broader context-loss-mitigation section gets written later, merge this into it rather than keeping two.)

**Every session starts by checking the immediately preceding PR for unaddressed review comments before starting new work** - the same discipline already applied to `docs/VISION.md`/`docs/OPEN_POINTS.md` at the start of a new task. A CI run going green does not mean a PR is done: a human reviewer, GitHub's own bots (CodeQL, Dependabot, secret-scanning alerts), or any other automated commenter can leave feedback after the fact, and nothing in this repo's process otherwise re-surfaces it.

Checklist for the PR(s) in scope:
- Pull all three comment surfaces, not just one: issue-level comments, inline review comments, and formal reviews (`pull_request_read` with `get_comments`/`get_review_comments`/`get_reviews`, or the equivalent for whatever tool is available) - a comment can land in any of the three.
- For each comment found: address it with a real code change if it's actionable, note explicitly if it's already stale/resolved by later work, or reply substantively if it's a question - never leave it silently unread.
- If the PR in question has already merged, don't rewrite merged history - open a new small follow-up PR/commit referencing the original instead.
- Report per PR explicitly, including "none found" - don't assume a PR has nothing just because it's old or because CI was green.
